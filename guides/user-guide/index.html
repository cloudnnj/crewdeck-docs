Introduction​

What is CrewDeck?​

CrewDeck is a desktop application that enables teams to manage and dispatch work to AI agents. Think of it as a project management tool (like Jira or Trello) specifically designed for AI-powered development workflows.

With CrewDeck, you can:

  • Organize work by team using Projects
  • Connect GitHub repositories to discover AI agents and commands
  • Create tasks on a visual Kanban board
  • Execute tasks with AI agents that write code, create branches, and open Pull Requests
  • Monitor progress in real-time through an integrated terminal

Key Concepts​

ConceptDescription
ProjectA logical grouping for your work — typically representing a team, project, or domain (e.g., "Engineering", "Frontend", "API Team").
RepositoryA GitHub repo connected to a project. Agents and commands are automatically discovered from connected repos.
AgentAn AI specialist that can execute tasks. Examples include "frontend-developer", "code-reviewer", and "database-designer".
CommandA slash command (e.g., /build-feature, /fix-bug) that defines a specific workflow an agent can run.
TaskA work item on the Kanban board. Tasks have a title, description, priority, and can be assigned to agents.
Task NumberA human-readable identifier automatically assigned to each task (e.g., "ENG-0001").
WorktreeA separate working directory for each task. This isolates changes and prevents conflicts with your local development.
ConfigClaude Code configurations including agents, skills, and commands, managed from the Agents, Commands and Skills tabs under Crew in the project header.
SkillA reusable workflow or specialized task automation that extends Claude's capabilities (e.g., /commit, /review-pr).
TemplatePre-built configurations that can be imported into a repository to quickly set up agents, skills, or commands.

Getting Started​

Prerequisites​

Before using CrewDeck, ensure you have:

  1. Node.js 18+ — Download from nodejs.org
  2. Git — Version control system
  3. GitHub Account — For repository integration
  4. GitHub Personal Access Token — With repo scope enabled
  5. A Claude account or Anthropic API key — Agents run on Claude (see LLM Setup)

Installation​

  1. Download the CrewDeck installer for your platform
  2. Run the installer and follow the on-screen instructions
  3. Launch the CrewDeck application

First-Time Setup​

Step 1: Connect GitHub​

CrewDeck supports two methods for authenticating with GitHub:

Option A: Device Flow (Recommended)

OAuth Device Flow (RFC 8628) needs no locally running redirect server, so it avoids port conflicts.

  1. Click the Settings gear at the right end of the menu bar
  2. On the Integrations tab, in the GitHub Integration section, click Sign in with GitHub
  3. CrewDeck displays a short user code (e.g., ABCD-1234)
  4. Visit github.com/login/device in your browser
  5. Enter the code and authorize CrewDeck
  6. The app detects authorization automatically and shows a green "Connected" status indicator

Option B: Personal Access Token (PAT)

  1. Click the Settings gear at the right end of the menu bar
  2. On the Integrations tab, in the GitHub Integration section, click the token input field
  3. Go to github.com/settings/tokens and create a Personal Access Token:
    • Click Generate new token (classic)
    • Give it a descriptive name (e.g., "CrewDeck App")
    • Select the repo scope (full control of private repositories)
    • Click Generate token and copy the token
  4. Paste the token into CrewDeck and click Connect GitHub
  5. You should see a green "Connected" status indicator

Step 2: Set Up Claude​

CrewDeck runs its AI agents on Claude. Packaged builds ship with the Claude Code runtime, so you do not need to install anything extra to run tasks. You do need to tell CrewDeck how to authenticate with Claude. Follow LLM Setup before you run your first task.

Step 3: Create Your First Project​

  1. Click the + button next to "Projects" in the sidebar
  2. Enter a name (e.g., "Engineering" or "My Project")
  3. Optionally add a description and choose a color
  4. Click Create Project

LLM Setup​

This section takes you from a fresh install to your first Claude-backed task run. Do it once, before you create tasks.

Step 1: Know What Is Already Installed​

Packaged CrewDeck builds include the Claude Code runtime that agents run on, so CrewDeck can run tasks without a separate install.

Install the Claude Code command-line tool yourself if you want to create an OAuth token for the recommended OAuth Token method (Step 2), or to drive Claude yourself in the interactive terminals:

npm install -g @anthropic-ai/claude-code

Settings → AI & Tools → Claude Code shows this install command for that purpose.

Step 2: Choose How CrewDeck Authenticates With Claude​

  1. Click the Settings gear at the right end of the menu bar
  2. Open the AI & Tools tab
  3. Find the Claude Authentication card ("Configure how CrewDeck authenticates with the Claude Code SDK.")
  4. Pick an authentication method. Your choice saves immediately.
MethodWhat it meansWhen to choose it
OAuth TokenRuns use one or more stored Claude account tokens. The Claude Accounts panel appears below the radio buttons.Recommended. Required for multiple accounts, auto-rotation and per-project account assignment.
API KeyRuns reuse your Anthropic API key. The card shows "Anthropic API key is configured" or "No Anthropic API key configured".You pay per token through the Anthropic Console. Store the key under Settings → Integrations → LLM Provider → Anthropic Platform API Key.
CLI Fallback"Claude Code CLI handles its own authentication. No additional configuration needed."You already signed in with the Claude Code command-line tool on this machine.
  1. Click Validate Authentication. A working setup shows Authentication valid. If you see Authentication invalid, re-check the token or key and validate again.

Getting an OAuth token. CrewDeck does not generate tokens itself. With the Claude Code command-line tool installed (Step 1), create one by running claude setup-token in a terminal and signing in with your Claude account, then paste the token it prints into CrewDeck (Step 3).

What you see if authentication is missing. On first launch, when no working Claude authentication is found, CrewDeck shows a one-time Configure Claude Authentication dialog with two options: OAuth (Recommended) and API Key.

  • Set Up OAuth or Set Up API Key selects that method and opens Settings so you can finish.
  • Skip for Now (or pressing Esc) selects CLI Fallback. You can change the method at any time in Settings → AI & Tools → Claude Authentication.

Step 3: Add Your Claude Accounts​

With OAuth Token selected, the Claude Accounts panel lists your stored accounts. It shows "No accounts added yet." until you add one.

  1. Under Add a new Claude account, enter a label in Account label (e.g. Personal, Work) (up to 50 characters)
  2. Paste the token into OAuth token
  3. Click Add Account. The panel confirms with "Account added".
  4. Repeat for each additional account, such as a personal account and a work account

Each account row shows:

  • An Active badge on the account used by default
  • A load badge (for example 1/3) showing active sessions against the per-account capacity
  • A Cooling down badge after the account hits a rate limit

Use Activate to make another account the default. Use Remove to delete one. There is no confirmation step, so check the label first.

Step 4: Control Rotation and Concurrency​

Two settings at the bottom of the Claude Accounts panel decide how sessions spread across accounts:

  • Enable auto-rotation on usage limit: "Automatically switch to the next account when rate-limited". This is off by default. Turn it on if you hold more than one account and want work to continue when one runs out.
  • Max concurrent sessions per account: "How many sessions the balancer runs on one account before spilling to the next". The default is 3 and the minimum is 1. Type a number and click Save, or click away from the field. Invalid values reset to 3.

Step 5: Assign Accounts to Each Project​

By default every project uses the active account. To give a project its own credit pool:

  1. Open the project and click the pencil Edit project button next to its name
  2. Find the Claude accounts card
  3. Tick each account this project should use
  4. Click Save Changes

See Claude accounts under Configuring a Project for exactly how sessions are distributed.

Step 6: Pick Default Providers and Models​

  • Edit Project → Default LLM provider sets the provider and model that the project's tasks use unless a task or substage overrides it.
  • Edit Project → Model by task size routes task execution to a different model per task size.
  • Edit Project → Substage settings pins a model, advisor and prompt per workflow substage.
  • Edit Project → AI budget sets an informational monthly spend budget.

App-wide keys for other providers (OpenAI, Google Gemini, xAI) are stored under Settings → Integrations → LLM Provider.

Step 7 (Optional): Set Up Local Models With Ollama​

Claude runs your tasks. A local Ollama install powers the built-in Chat, task embeddings for semantic search, agent recommendations and daily summaries. Ollama is optional: when it is not running, these features fall back to simpler behaviour or show as unavailable, and task execution with Claude is unaffected.

  1. Install Ollama and start it (ollama serve, or open the Ollama desktop app). CrewDeck connects to http://127.0.0.1:11434.
  2. Pull the chat and embedding models: 
    ollama pull qwen3:8b
    ollama pull nomic-embed-text
  3. In Settings → AI & Tools → Ollama Chat Model, confirm or change the chat model (default qwen3:8b) and click Save
  4. Optionally use Recommended Local Models → Pull all recommended to download the curated models, and Model Management to add custom model IDs for any provider
  5. To answer agent chats with Claude instead of Ollama, turn on Use Anthropic for Agent Chat. It needs an Anthropic API key.

Codex users: Settings → AI & Tools → Codex Authentication offers Device Code (click Sign in with Device Code and enter the code shown at the given address) or OpenAI API Key. The current Codex runner requires the OpenAI API key method.

Step 8: Verify With a First Run​

  1. Create a project and connect a repository (see Connecting GitHub Repositories)
  2. Create a small task and assign an agent (see Configuring a Task)
  3. Click Run on the task card (see Running a Task)

If the run fails to start with an authentication error, return to Settings → AI & Tools → Claude Authentication and click Validate Authentication.

Connecting GitHub Repositories​

To use AI agents, you need to connect at least one GitHub repository that contains agent definitions.

Prerequisites​

  • GitHub must be connected in Settings (see First-Time Setup)
  • You need access to at least one GitHub repository

Connecting a Repository​

  1. Navigate to your project
  2. Click the Repos tab
  3. Browse the list of available repositories from your GitHub account
  4. Click Connect next to the repository you want to add
  5. Wait for the repository to be cloned locally (this may take a moment for large repos)
  6. Once connected, CrewDeck automatically scans for agents and commands

What Gets Discovered​

CrewDeck scans connected repositories for:

DirectoryContentResult
.claude/agents/Agent definition filesAvailable agents appear in the Agents tab
.claude/commands/Command definition filesAvailable commands appear in the Commands tab

Syncing Agents and Commands​

If you update agents or commands in your repository, use the Refresh button to pull changes and re-discover configurations:

  1. Go to the Repos tab in CrewDeck
  2. Click the Refresh button (circular arrow icon) next to the repository
  3. CrewDeck will:
    • Pull the latest changes from the remote repository
    • Re-scan for agents and commands
    • Update the agent/command lists automatically

Refresh Button Behavior

Repository TypeAction
Primary/Context ReposPulls latest, re-discovers agents and commands
Marketplace ReposPulls latest, re-discovers marketplace agents

Error Handling

The refresh operation may fail in certain situations:

ErrorCauseSolution
Uncommitted changesRepository has modified filesCommit or stash changes before refreshing
Network errorNo internet connectionCheck your connection and retry

An error banner displays with specific instructions when refresh fails. Click the X to dismiss it.

Disconnecting a Repository​

  1. Go to the Repos tab
  2. Click Disconnect next to the repository you want to remove

Creating a New Repository​

Instead of creating a repository on GitHub first and then connecting it, you can create a new GitHub repository directly from CrewDeck.

How to Create a New Repository

  1. Navigate to your project's Repos tab
  2. Click the Create New Repo button (next to the repository list header)
  3. Fill in the repository details:
FieldRequiredDescription
Repository NameYesLetters, numbers, hyphens, underscores, and periods only. Cannot start with a period or end with .git. Max 100 characters.
DescriptionNoA brief description of the repository
VisibilityYesPrivate (default) or Public
Initialize with READMENoChecked by default; creates an initial README file
  1. Click Create Repository
  2. CrewDeck will:
    • Create the repository on GitHub
    • Clone it locally
    • Connect it to the project
    • Run agent and command discovery

Error Handling

If the clone step fails after the GitHub repository has been created, CrewDeck automatically deletes the orphaned GitHub repository to prevent leftover resources.

ErrorCauseSolution
Repository name already existsA repo with the same name exists on your GitHub accountChoose a different name
Clone failedNetwork error or permissions issueThe orphaned repo is cleaned up automatically; retry the operation
Permission deniedToken lacks sufficient permissionsEnsure your token has the repo scope

Primary and Context Repositories​

When a project has multiple connected repositories, CrewDeck distinguishes between them using primary and context designations.

How It Works

DesignationDescription
PrimaryThe main working repository where code changes happen. The first connected repo is automatically set as primary. Shown with a blue "Primary" badge.
ContextAdditional repositories that provide supplementary documentation. Shown with a purple "Context" badge when multiple repos are connected.

Context repos contribute documentation from their docs/ folders and PROJECTS.md files to enhance AI-generated agent and command suggestions in the Generate wizard on the Agents, Commands and Skills tabs.

Changing the Primary Repository

  1. Navigate to the Repos tab
  2. Find the context repository you want to make primary
  3. Click the Set Primary button
  4. The previous primary becomes a context repository
  5. Context caches are automatically refreshed

Context in Config Generation

When using the Generate wizard on the Agents, Commands or Skills tab:

  1. CrewDeck automatically fetches documentation from context repos
  2. A purple indicator shows "Context available from N connected repos"
  3. This context is included in the AI generation prompt for more relevant suggestions

Repository Onboarding Wizard​

When you connect a new repository that doesn't have Claude configurations, CrewDeck offers an onboarding wizard to help you set up agents, skills, and commands quickly.

When the Wizard Appears​

The onboarding wizard appears when:

  • A repository is first connected to a project
  • The repository lacks existing .claude/ configuration directories
  • You haven't previously dismissed the wizard for this repository

Wizard Steps​

StepNameDescription
1AgentsSelect pre-built agents to import (e.g., frontend-developer, code-reviewer)
2SkillsSelect skills to import (e.g., commit, review-pr, build-feature)
3CommandsSelect commands to import (e.g., /fix-bug, /create-pr)
4ConfirmReview your selections and create the PR

Using the Wizard​

Step 1: Select Agents

  • Browse available agent templates
  • Check the agents you want to add
  • Each agent shows its name, description, and capabilities
  • Click Next to continue

Step 2: Select Skills

  • Browse available skill templates
  • Check the skills you want to add
  • Skills are reusable workflows like /commit or /review-pr
  • Click Next to continue

Step 3: Select Commands

  • Browse available command templates
  • Check the commands you want to add
  • Commands are task-specific automations
  • Click Next to continue

Step 4: Confirm

  • Review all selected configurations
  • See a summary of what will be created
  • Click Create PR to proceed

After Completion

  1. Configuration files are generated in the repository
  2. A feature branch is created
  3. A Pull Request is opened on GitHub
  4. Merge the PR to activate the configurations
  5. Sync the repository to see the new configurations in CrewDeck

Skipping the Wizard​

If you prefer to set up configurations manually or later:

  • Click Skip or Later to dismiss the wizard
  • You can always use the Add from Templates or Generate features on the Agents, Commands and Skills tabs later

Configuring a Project​

Projects are the top-level organisational units. Each project has its own Kanban board, connected GitHub repositories, discovered agents and commands, and its own configuration.

Creating a Project​

  1. In the sidebar, click the + button next to "Projects"
  2. Fill in the project details:
    • Name (required): A short identifier (e.g., "Backend", "Mobile")
    • Description (optional): A brief explanation of the project's purpose
    • Color: A preset colour to tell projects apart
  3. Click Create Project

Navigating Projects​

  • Click any project in the sidebar to open it
  • Dashboards, at the top of the sidebar, opens the cross-project dashboards (see Dashboards)

Opening the Edit Project Panel​

  1. Open the project
  2. Click the pencil Edit project button next to the project name in the header

The Edit Project Settings panel opens beside the Board. Use Find a setting… to jump to a card. The section index groups the cards under Project, Workflow, Agents & models, Spend and Irreversible.

How each card saves

Every card carries one of three save labels:

The footer shows No unsaved changes when there is nothing to save. Closing with unsaved changes asks whether to Keep editing or Discard.

The cards appear in the order below.

Saves with the form.

FieldWhat it does

Branching Strategy​

Saves with the form. "Agents open PRs into the integration branch; releases cut from it into the release branch."

  • Integration branch (for example develop): task worktrees branch from here and agent PRs target it
  • Release branch (for example main): releases are cut from the integration branch into this branch

Leave both at the repository's default branch for a simple trunk-based flow. Set a separate integration branch for a GitFlow-style flow. New task executions use the new branches. Existing task worktrees keep the branch they were created from.

Related Projects​

Auto-saves. "Link the projects this one builds on and the ones that build on it. Agents here can file requests only in linked projects."

  1. Under Link a project, choose a direction: ↑ Upstream (this project builds on it) or ↓ Downstream (it builds on this project)
  2. Pick the Project
  3. Optionally describe what the project uses it for. Agents read this text.
  4. Click Link project

Linked projects appear under ↑ Upstream and ↓ Downstream. Use Unlink to remove a link.

Kanban Stages​

Saves with the form. Choose which columns appear on the board. To Do and Done are always shown and marked Required. The optional stages can be switched off per project:

StageWhen to switch it off
In ProgressSimple projects where tasks go straight from To Do to Done
In ReviewProjects without a formal code review step
DocumentProjects that produce no documentation artifacts

You can also choose stages in the Create Project form.

When a stage is switched off, tasks whose status belongs to that stage are shown in the nearest preceding enabled column. This only changes the display; the task's stored status is unchanged. Switching the stage back on returns those tasks to their own column.

Task Execution​

Saves with the form. A numbered timeline of the commands that run at each stage:

  • In Progress Pre-Step and In Progress Mid-Step: commands that run before and during the main build
  • Review Command: what runs when a task enters review
  • Improve Command: what runs to address review findings
  • Document Command: what runs in the Document stage

Each slot has its own continue-on-error toggle. Below the timeline, Test commands holds one shell command per repository (for example npm test -- --run).

PR Fix Commands​

Saves with the form. "What runs when you click a fix action on a failing PR."

  • Fix Tests Command
  • Fix Code Quality Command (Codacy or SonarCloud findings)
  • Resolve Conflicts Command
  • Fix CI Command

Context Repos​

Saves with the form. This card appears only when a context repository is connected to the project.

  • Always read from context repos: "New tasks default to reading docs and PROJECTS.md from context repositories". Individual tasks can still change this with Read from Context Repos in the task form.

See Primary and Context Repositories.

Default LLM Provider​

Auto-saves. "Tasks in this project use this provider unless overridden per-task or per-substage."

  • Provider: the LLM provider for the project. Some features are marked Anthropic-locked because they always run on Claude.
  • Model: a model from the provider's list, or Custom model ID.... Use default clears the override.

Claude Accounts​

Saves with the form. "Assign this project's Claude Code runs to specific OAuth accounts so parallel work across projects draws from separate credit pools."

Tick each stored account this project should use, then click Save Changes. Add accounts first under Settings → AI & Tools → Claude Authentication (see LLM Setup).

SituationWhat happens
No accounts tickedRuns use the active account selected in Settings → AI & Tools
One account tickedEvery AI run started from the project uses that account
Several accounts tickedEach new agent session gets the least-busy assigned account, so concurrent work spreads across them
Auth method is not OAuthThe card explains that per-project assignment applies only to OAuth; every project uses the configured credentials
An assigned account was removedIts sessions fall back to the default account. Click Drop stale to clean up the list.

When an assigned account hits a rate limit, CrewDeck stops sending it new sessions for a few minutes and may retry the project's runs with another stored account. If every assigned account is busy, runs still start on the least-loaded one instead of failing. The app-wide active account is never changed by this.

Account assignment applies to agent sessions CrewDeck runs for you. Terminal sessions you drive yourself use whatever account the Claude Code command-line tool is signed in to.

Substage Settings​

Auto-saves. "Model, advisor and prompt per substage. Rows follow your enabled Kanban stages."

Each row covers one workflow substage:

  • Provider and model: pin a model for that substage, or Reset to inherit
  • Advisor mode and Advisor model: have a second model review the substage's work
  • Prompt override: replace the substage prompt for this project. Use app default restores the built-in prompt; Save stores your edit.
  • Enable migration: shown on substages that support it

Model by Task Size​

Auto-saves. "When on, the task-execution substage uses the model mapped to the task's size. Unmapped sizes, and tasks with no size, use the normal model selection."

  1. Turn on Route task execution by task size (off by default)
  2. Pick a provider and model for each size, or leave it on Default

Turning the toggle off keeps the sizes you mapped.

MCP Servers​

Saves with its own button. Tick the MCP servers this project's agents may use, then click Save.

  • Servers marked Bundled ship with CrewDeck
  • Servers marked Available on Pro need a Pro plan or an active trial. Without one they are not given to agent runs.

  • Gray badge: All blocking dependencies are resolved (task is ready)
  • Count: Number shown indicates total dependencies

  • Depends On: Tasks this task depends on (with status indicators)
  • Required By: Tasks that depend on this task (reverse lookup)

Dependency Enforcement

The dependency system enforces constraints at multiple layers:

  • UI: You cannot drag a task with unresolved blocking dependencies to "In Progress"
  • Backend: API calls to start tasks with unresolved blocking dependencies are rejected
  • Database: Circular dependencies are detected and prevented using DAG validation

Circular Dependency Prevention

CrewDeck automatically detects circular dependencies using a recursive database query:

  • If adding a dependency would create a cycle (A depends on B, B depends on A), the operation is rejected
  • This validation runs for all dependency types, not just "blocks"
  • Maximum dependency chain depth is limited to 100 levels for safety

Auto-Chaining for Generated Tasks

When you use the Generate Tasks or Dispatch Tasks features:

  • Tasks are automatically linked with sequential "blocks" dependencies
  • Task 2 depends on Task 1, Task 3 depends on Task 2, etc.
  • This creates an automatic execution pipeline for batch-generated work

AI-Driven Dependency Suggestions

CrewDeck can automatically suggest dependencies based on task content and project context. This feature uses AI to analyze task descriptions and recommend which tasks should depend on others, helping you build accurate dependency graphs without manual analysis.

Example Workflows

Frontend/Backend Split:

Parallel Work with Final Integration:

  • Task A: "Design database schema" (no dependencies)

Task Intelligence and Semantic Search​

CrewDeck includes an AI-powered task intelligence system that generates semantic embeddings for tasks and enables similarity-based search to find related work.

What are Task Embeddings?

Task embeddings are 768-dimensional vector representations of your task titles and descriptions. They capture the semantic meaning of tasks, allowing the system to find conceptually similar tasks even when they use different wording.

Generating Embeddings

Task embeddings are generated automatically in the background using a local Ollama model (nomic-embed-text). No external API keys are required — the system runs entirely on your local machine.

  1. Ensure Ollama is running locally with the nomic-embed-text model pulled
  2. Embeddings are generated automatically when tasks are created or updated
  3. Embeddings are cached locally in SQLite

Finding Similar Tasks

Use semantic search to find tasks related to your current work:

  1. Open any task detail view
  2. Click Find Similar Tasks
  3. The system searches for tasks in the same project with high similarity scores
  4. Results show similarity percentages and highlight conceptually related work

Similarity Scoring

  • Cosine similarity algorithm compares embedding vectors
  • Minimum similarity threshold: 30%
  • Only compares tasks within the same project
  • Results ranked by relevance (highest similarity first)

Keyword Fallback

If Ollama is unavailable, the system automatically falls back to TF-based (term frequency) keyword matching:

  • Tokenizes task text and removes stop words
  • Computes term frequencies
  • Maps to a 100-dimensional keyword vector
  • Provides basic similarity search without local model dependency

Circuit Breaker Protection

The system includes a circuit breaker to prevent cascading failures:

  • Closed: Normal Ollama operation
  • Open: After 3 consecutive failures, switches to keyword fallback for 60 seconds
  • Half-Open: After cooldown, tries one Ollama call. Success closes circuit; failure reopens it

Use Cases

  • Find previous tasks that solved similar problems
  • Identify duplicate or overlapping work
  • Discover related tasks for dependency planning
  • Build context when starting new tasks

Privacy & Security

  • Embeddings generated locally via Ollama — no data sent to external APIs
  • Embeddings cached locally in SQLite
  • Expired embeddings automatically cleaned up after TTL

Sequential, Swarm, and Team Execution Modes​

When assigning two or more agents to a task, you can choose how those agents execute by selecting an Agent Execution Mode. The mode toggle appears automatically when 2+ agents are assigned.

Choosing an Execution Mode

  1. When creating or editing a task, assign 2 or more agents
  2. The Agent Execution Mode toggle appears below the agent list
  3. Click Sequential, Swarm, or Team to select your mode

Execution Modes

ModeDescriptionBest For
Sequential (default)Agents execute one after another in the order listed. Each agent must complete before the next starts.Predictable workflows where order matters (e.g., build then test)
SwarmAn orchestrator agent coordinates subagents dynamically using Claude's Task tool, enabling parallel work within a single session.Complex tasks where multiple specialists can work simultaneously but share context
TeamA lead agent spawns fully independent Claude Code teammate instances that communicate via shared task lists and messaging.Large-scale tasks requiring truly independent agents with separate context windows

Sequential Mode Details

  • Agents run in the exact order they appear in the agent list
  • If an agent fails, execution stops and the remaining agents do not run
  • Terminal output shows clear markers for each agent's execution: Agent: @agent-name
  • In relay mode, each agent can pass structured context to the next agent via handoff files, enabling explicit knowledge transfer between sequential steps.

Swarm Mode Details

  • An orchestrator agent is used to coordinate work across subagents using Claude's Task tool
  • If the first selected agent is an orchestrator type (e.g., feature-orchestrator, bugfix-orchestrator), it is used as the coordinator
  • If no orchestrator is selected, the first agent in the list becomes the coordinator
  • Subagents run within the orchestrator's session and share the same context window
  • Terminal output indicates swarm mode with: Swarm Execution (Orchestrated)

Team Mode Details

  • Uses Claude Code's experimental Agent Teams feature
  • A lead agent (preferably an orchestrator) coordinates fully independent teammate instances
  • The lead uses TeamCreate, TaskCreate, and SendMessage tools to spawn and manage teammates
  • Each teammate is a fully independent Claude Code instance with its own context window
  • Teammates self-coordinate via a shared task list and can communicate directly
  • Best suited for very large tasks where each agent needs complete independence
  • Terminal output indicates team mode with: Team Execution (Agent Teams) in amber

Example Workflows

Sequential: Assign frontend-developer and code-reviewer to a task. The frontend developer implements the feature first, then the code reviewer analyzes the output.

Swarm: Assign feature-orchestrator, frontend-developer, and backend-developer. The orchestrator coordinates both developers using the Task tool to work on their respective portions.

Team: Assign feature-orchestrator, frontend-developer, backend-developer, and database-designer for a large multi-component feature. The orchestrator spawns each as an independent teammate with full context isolation.

DAG Execution Mode​

The DAG (dependency graph) execution mode runs a task's agents in an order you draw, starting each agent as soon as the agents it depends on have finished.

When to use it

  • One agent's output feeds directly into another agent's work
  • Some agents should run only after others complete
  • You want independent agents to run in parallel automatically
  • A large team (five or more agents) needs a clear execution order

Setting up a DAG

  1. Create or edit a task with several agents
  2. Under Agent Execution Mode, choose DAG
  3. The graph builder shows each agent as a node
  4. Drag from one agent to another to add a dependency (an arrow from A to B means A must finish before B starts). Click an arrow to remove it.
  5. Save the task

The builder rejects circular dependencies and can reset the graph to start over. During a run, finished agents are highlighted and agents that are ready to run are shown in blue.

How it runs

  • Agents with no dependencies start immediately
  • Each other agent waits until all of its dependencies have finished
  • Agents run in parallel whenever their dependencies allow
  • If an agent fails, the agents that depend on it do not start

Pause and Resume Task Execution​

CrewDeck allows you to pause long-running task executions and resume them later, preserving the Claude CLI conversation context.

Pausing a Running Task

  1. Locate a task with an active running session (look for the session indicator on the task card)
  2. Click the amber Pause button (⏸) next to the session indicator
  3. A confirmation dialog appears asking you to confirm the pause — this prevents accidental interruption of long-running agent work (see Terminal Session Confirmation Dialogs)
  4. Confirm the pause to gracefully terminate the PTY process and save the execution state
  5. The task shows a "Paused" indicator with the pause timestamp

What Gets Saved

When you pause a task, CrewDeck saves:

  • Claude CLI session ID for resume capability
  • Current command chain position (if using command chaining)
  • Execution phase at time of pause
  • Assigned agent IDs
  • Worktree path and branch name

This state is persisted to a .crewdeck-pause-state.json file in the task's worktree.

Resuming a Paused Task

  1. Locate the paused task (it will show an amber "Paused" badge)
  2. Click the Resume button (▶)
  3. CrewDeck spawns a new terminal session and attempts to resume using Claude CLI's --resume flag
  4. If a session ID is available, it runs: claude --resume "<session-id>"
  5. If no session ID is found, it uses: claude --continue to continue from the last checkpoint

Resume Behavior

  • The resumed session picks up where the paused session left off
  • Claude maintains conversation context across the pause/resume cycle
  • Terminal output continues in a new session
  • If resume fails, the pause state is restored so you can try again

Use Cases

  • Resource management: Pause tasks to free up terminal sessions for higher-priority work
  • Work breaks: Pause long-running tasks during breaks without losing context
  • Session limits: Manage concurrent session limits by pausing lower-priority tasks
  • Context preservation: Keep Claude's conversation state across application restarts

Session Resume​

In addition to pausing and resuming the current task, CrewDeck supports resuming a specific previous Claude CLI session by ID. This is useful when you want to return to an earlier session that was not paused through the standard flow.

Using Session Resume

  1. Open the terminal panel for a task that has an existing worktree
  2. Click the Resume Session button in the terminal toolbar
  3. A session picker dialog appears listing recent Claude CLI sessions associated with this task
  4. Select the session you want to resume
  5. CrewDeck spawns a new PTY with claude --resume "<session-id>"
  6. Claude restores the conversation context from the selected session

When to Use Session Resume

  • Application restart: Resume a session that was running before CrewDeck was restarted
  • Crash recovery: Pick up a session that was interrupted by a crash or system sleep
  • Exploratory work: Return to a previous session to try a different approach

Limitations

  • Session resume requires the original worktree to still exist
  • If Claude CLI cannot find the session (e.g., it was garbage-collected), an error is displayed in the terminal
  • Only sessions from the current task's worktree are shown in the picker

Sleep Prevention​

Applies to: all task execution sessions (CLI, Codex and SDK). Sleep prevention is requested when a task session starts, whichever execution path it uses.

CrewDeck automatically prevents your computer from going to sleep while active terminal sessions are running, ensuring long-running AI agent tasks are not interrupted.

How It Works

Sleep prevention activates automatically using Electron's built-in powerSaveBlocker API:

  • Automatic activation: When the first terminal session spawns (interactive or task execution)
  • Reference counting: Sleep prevention stays active as long as at least one session is running
  • Automatic deactivation: When the last terminal session exits or is killed
  • Cross-platform: Works on macOS, Windows, and Linux

Blocker Type

CrewDeck uses the prevent-app-suspension blocker type:

  • System sleep: Prevented — your machine stays awake
  • Display sleep: Allowed — your screen can turn off to save power
  • Background operation: Enabled — sessions continue running even with display off

Manual Control

You don't need to manually run caffeinate or adjust system settings. Sleep prevention is fully automated based on terminal session lifecycle.

Status Visibility

While sleep prevention doesn't have a visible indicator in the UI, you can verify it's active by checking:

  • System settings show the application preventing sleep
  • macOS Activity Monitor shows CrewDeck preventing idle sleep
  • Your system won't go to sleep automatically during active agent execution

Clean Shutdown

Sleep prevention is forcefully stopped when:

  • You quit CrewDeck
  • All terminal sessions are terminated
  • The application is restarted

App Refresh Protection​

Applies to: sessions counted as active terminal sessions.

CrewDeck prevents accidental renderer refreshes (Cmd+R, Ctrl+R, F5) when active terminal sessions exist, protecting you from losing running AI agent work and wasted Claude API tokens.

Two-Layer Defense

CrewDeck uses defense-in-depth with independent safety layers:

Layer 1: Main Process Interception (Primary)

  • Intercepts keyboard shortcuts: Cmd+R, Ctrl+R, Cmd+Shift+R, Ctrl+Shift+R, F5
  • Queries active terminal session count
  • Shows a native confirmation dialog when sessions are running
  • Dialog displays:
    • Warning icon and session count
    • Risk explanation (API token waste, task interruption)
    • "Cancel" (default) and "Refresh Anyway" buttons
  • Allows normal refresh when no sessions are active

Layer 2: Renderer beforeunload Handler (Secondary)

  • Catches edge cases like programmatic refreshes or browser-triggered navigation
  • Checks Zustand store for running sessions
  • Calls preventDefault() to trigger browser warning prompt
  • Only activates when running sessions exist

User Experience

ScenarioBehavior
Cmd+R with 0 sessionsRefreshes normally without prompt
Cmd+R with 1+ sessionsNative dialog shows warning, blocks refresh by default
User clicks "Cancel"Page stays loaded, sessions continue running
User clicks "Refresh Anyway"Page reloads (explicit confirmation)
F12, Zoom shortcutsStill work normally (not intercepted)

Why This Matters

Accidental refreshes during AI agent execution:

  • Destroy WebContents sender references, orphaning PTY sessions
  • Waste Claude API tokens from interrupted mid-task processing
  • Lose session state (although reconnection exists as a safety net)

Terminal Sandboxing

All renderer windows run in Electron sandbox mode (sandbox: true). Refresh protection also accounts for the sandboxed renderer context: if the renderer is compromised or in an unexpected state, the main-process interception layer (Layer 1) continues to function independently, maintaining protection even when the renderer beforeunload handler cannot fire.

Dialog Behavior

  • Only one dialog shown at a time (prevents stacking from rapid key presses)
  • Native dialog blocks event loop (appropriate for critical confirmation)
  • Works even if renderer is in a bad state
  • Session count checked at time of keypress (TOCTOU consideration: if sessions complete while dialog is open, refreshing is harmless)

PR Watcher​

The PR Watcher scans a project's open pull requests on a schedule, auto-merges the eligible ones and dispatches fix agents for failing checks. Its settings live in Settings → Autonomy → PR Watcher; the poll-mode controls appear once the watcher is enabled for the project.

Poll modes

ModeWhat drives scans
Poll (default)An interval scan every 5 minutes (or the project's configured interval, never faster than 30 seconds)
HybridWebhook deliveries, plus a reconcile scan at most every 6 hours — only while the project has an active webhook subscription
WebhookWebhook deliveries only, with no interval scan — only while the project has an active webhook subscription

Fallback rule. Hybrid and Webhook need an active webhook subscription for the project's primary repository. Until one exists, both modes fall back to polling at the configured interval, exactly like Poll mode. The 6-hour reconcile floor and the timer-less webhook mode apply only while a subscription is active. Hybrid and Webhook also fall back to polling while this desktop is signed out of CrewDeck Cloud, or signed in on a plan without PR Watcher.

Enabling webhook delivery.

  1. Sign in to CrewDeck Cloud (Settings → CloudSync).
  2. Be on a plan that includes PR Watcher: trial, Pro or Founder.
  3. Choose Hybrid or Webhook in Settings → Autonomy → PR Watcher. The relay section appears only for those two modes.
  4. CrewDeck creates the GitHub webhook on the project's primary repository itself. There is no URL or token to enter.

If this desktop is signed out, the relay section shows "Sign in to CrewDeck Cloud to receive PR Watcher webhooks." with a Sign in button. If your plan does not include the feature, it shows "PR Watcher webhooks aren't included in your plan" instead.

Relay status. A status pill shows the connection to CrewDeck's webhook relay:

StatusMeaning
Connected (green)Deliveries arrive within seconds.
Connecting / Reconnecting (amber, pulsing)The relay connection is opening or re-opening. Deliveries made meanwhile are queued and replayed on reconnect, each processed once.
Error (red)The connection failed; the reason is shown next to the pill.
Disconnected (grey)No relay connection.

Delivery URL and Reset URL. The relay section shows this desktop's delivery URL read-only ("Delivery URL not issued yet" until the relay has issued one). Reset URL issues a new delivery URL; the old one keeps working for 24 hours, and the GitHub webhooks are repointed automatically. When the button is disabled, the reason is shown beside it: "Resetting the delivery URL…", "Available once the relay is connected." or "Available once the relay has issued a delivery URL."

Caution: the delivery URL is a capability: anyone who has it can post deliveries to this desktop. Do not paste it publicly, and reset it if it leaks.

While signed out. The GitHub webhooks stay registered. Deliveries queue in the cloud for up to 7 days (up to 500 per desktop) and are replayed after the same account signs back in.

Privacy. GitHub webhook payloads pass through, and are briefly stored encrypted in, CrewDeck's cloud relay. They are deleted on acknowledgement or after 7 days.

Seeing the real cadence. Under the poll-mode selector, an effective-interval line shows what the watcher is actually doing, e.g. "Scanning every 5m", "Scanning every 5m (interval fallback)" or "Webhook-driven; reconcile scan every 6h". When a webhook mode is running on its fallback, an amber warning explains why and which interval is in use instead:

  • "Sign in to CrewDeck Cloud to receive PR Watcher webhooks. The watcher is polling every 5m instead."
  • "Your plan does not include PR Watcher webhooks. The watcher is polling every 5m instead."
  • "Webhook delivery is unavailable (reason). The watcher is polling every 5m instead."
  • "No active webhook subscription for this project's primary repository. The watcher is polling every 5m instead."

If auto-merge seems slow. Builds released before this fallback existed created new projects in Hybrid mode and scanned them only every 6 hours. Builds that include the fallback correct this automatically. On an older build, switch the project to Poll and trigger a scan from the developer console:

await window.api.prWatcher.updateSettings('<projectId>', { pollMode: 'poll' })

Capability-Based Agent Permissions​

Each agent manifest includes a capabilities array:

name: frontend-developer
capabilities:
  - file:read

Cross-Task Learning​

CrewDeck automatically learns from completed task executions and enriches new task prompts with relevant historical patterns, enabling AI agents to improve over time.

How It Works

Cross-task learning operates in two phases:

Phase 1: Extraction (on task completion)

When a task transitions to "done" status:

  1. Fetches task details, outcome, agents, commands, and terminal output
  2. Builds structured patterns (agent configuration, command sequences, execution mode, duration)
  3. Extracts error/resolution pairs from terminal output via regex heuristics
  4. Extracts key decisions from agent trace events
  5. Calculates a quality score (0-100) based on outcome status, user rating, and error count
  6. Stores the learning with upsert semantics (one learning per task)
  7. Ensures an embedding exists for semantic similarity matching

Phase 2: Injection (before task execution)

When a task is about to execute:

  1. Checks if cross-task learning is enabled (feature flag in settings)
  2. Uses 500ms timeout-protected query to fetch relevant learnings
  3. Finds semantically similar tasks via TaskIntelligenceService
  4. Filters learnings by project scope, minimum similarity (0.4), and minimum quality (30)
  5. Formats top 3 learnings as markdown with agent config, commands, errors, decisions, and outcome
  6. Appends the formatted context to the task description before passing to AI agent

Learning Data Structure

Each learning captures:

FieldDescription
PatternsAgent IDs/names, command info, execution mode, duration, outcome status
Error ResolutionsError/resolution pairs extracted from terminal output (max 10 pairs)
Key DecisionsDecisions from agent trace events (description, phase, confidence)
Output SummaryTruncated terminal output (max 10KB) with priority retention (first 20% + last 80%)
Quality Score0-100 score based on outcome, user rating, and error count

Quality Scoring Algorithm

Base score:
  success  → 80
  partial  → 50
  failure  → 20
  unknown  → 20

User rating bonus (if rated 1-5):
  bonus = (rating - 3) * 5    // Range: -10 to +10

Error penalty:
  penalty = min(10, errorCount * 2)

Final = clamp(base + bonus - penalty, 0, 100)

Turning It On or Off

Learning from past runs is controlled by the Agent Intelligence toggle (see Settings → Agent Intelligence).

Similarity Matching

The service uses TaskIntelligenceService embeddings to find relevant historical learnings:

  • Minimum similarity threshold: 0.4 (40%)
  • Minimum quality threshold: 30 (out of 100)
  • Maximum results: 3 learnings per prompt
  • Project-scoped: Only learnings from the same project are considered

Formatted Learning Context

Learnings are injected into task descriptions as markdown:

## Historical Learnings from Similar Tasks

### Learning 1: <Task Title> (Similarity: 85%)
**Outcome**: Success
**Agent Configuration**: backend-developer, database-designer
**Commands Used**: /build-feature
**Execution Mode**: sequential
**Duration**: 12.5 minutes

**Errors Encountered**:
- `ECONNREFUSED: Connection refused` → Resolved by starting PostgreSQL service
- `Module not found: bcrypt` → Resolved by running npm install bcrypt

**Key Decisions**:
- Used JWT tokens instead of session cookies for better scalability
- Implemented rate limiting at middleware level

Fire-and-Forget Extraction

Learning extraction is non-blocking to avoid slowing down task completion:

  • Runs in background with Promise.catch() only
  • Task update succeeds even if extraction fails
  • Errors are logged but don't interrupt the workflow

Timeout-Protected Injection

Learning injection never delays task execution:

  • Uses Promise.race with 500ms timeout
  • If similarity query takes too long, task proceeds without historical context
  • Prevents blocking the critical path for task execution

Use Cases

  • Error Prevention: Avoid repeating resolved errors from past tasks
  • Best Practices: Propagate successful patterns and agent configurations
  • Decision Guidance: Surface key decisions that led to good outcomes
  • Efficiency: Reduce trial-and-error by learning from historical data

Privacy & Scoping

  • Learnings are project-scoped (no cross-project contamination)
  • Terminal output is truncated to prevent sensitive data leakage
  • Stored in local SQLite database (not shared externally)
  • Turn the feature off with the Agent Intelligence toggle in Settings

Agent Intelligence and your data (ADR-0026)

Agent Memory and Cross-Task Learning are pinned to local AI processing. Extraction and similarity matching for both features run entirely on your local Ollama model — task content, terminal output, and stored memory or learning entries are never sent to a cloud AI provider (Anthropic, OpenAI, Gemini, or xAI), regardless of which provider you have selected elsewhere in CrewDeck.

This is enforced in code, not just by convention: a privacy-pinned prompt that resolves to any non-Ollama provider is refused and routed to the local model instead. If Ollama is unavailable, extraction is skipped rather than retried remotely.

Event Sourcing​

CrewDeck implements an event sourcing pattern to maintain a complete, immutable audit trail of all state changes in the system.

What is Event Sourcing?

Event sourcing captures every state change as an append-only event in the state_events table. Instead of just storing current state, the system records every transition, allowing you to:

  • Replay history to reconstruct past states
  • Audit all changes for compliance and debugging
  • Analyze patterns in how tasks and agents evolve over time

What Events Are Captured

The system tracks events for:

  • Tasks: Created, updated status, assigned agents, dependencies added
  • Agents: Discovered, updated, removed
  • Releases: Created, updated, published
  • Terminals: Session started, output written, session ended
  • All other entities: Any state mutation triggers an event

Event Structure

Each event includes:

  • Entity type: What was changed (task, agent, release, etc.)
  • Entity ID: Which specific instance was changed
  • Action: What happened (created, updated, deleted, etc.)
  • Previous state: Snapshot of data before the change
  • New state: Snapshot of data after the change
  • Metadata: Additional context (user ID, timestamp, etc.)
  • Timestamp: When the event occurred

Viewing Event History

Access event history through the API:

// Get all events for a specific task
const events = await window.api.events.getByEntity('task', taskId)

// Filter events by action type
const events = await window.api.events.list({ action: 'task:updated' })

// Count events in a time range
const count = await window.api.events.count({ startDate, endDate })

Event Retention

  • Events are retained for 90 days by default
  • Cleanup runs automatically to remove expired events
  • Maximum 1 million events stored at any time
  • Old events are deleted in batches to avoid blocking

Performance Optimizations

  • Deferred writes: Events are batched using setImmediate() to avoid blocking the event loop
  • Single transactions: Batched events are written in one transaction for efficiency
  • Emergency flush: If more than 10,000 events are pending, emergency batch writes are triggered
  • Sensitive data filtering: Fields like passwords and API keys are automatically stripped from snapshots

Use Cases

  • Debugging: Replay events to understand how a task reached its current state
  • Compliance: Maintain audit trails for regulated environments
  • Analytics: Analyze patterns in task state transitions
  • Conflict resolution: Understand conflicting changes in collaborative scenarios
  • Time travel: Reconstruct system state at any point in the past

Architecture

The event sourcing system uses a Change Data Capture pattern:

  • Entity tables (tasks, agents) remain the source of truth
  • State changes are written to entity tables as normal
  • Events are recorded in parallel to state_events as an audit log
  • Events never modify entities; they are append-only records

Autonomy Toggle​

Autonomy: "Automatically advance tasks through columns after successful execution".

Despite its label, this switch does not control the column move itself. When a stage finishes successfully, the task moves to the next column your project has enabled, whether or not Autonomy is on. The stages run in this order: To Do, In Progress, In Review, Document, Done. If your board has no In Review or Document column, the task skips ahead to the next one it does have.

What Autonomy adds is that CrewDeck starts the next stage for you after that move:

Task moved toWhat happens
In Progress, In Review or DocumentThat stage starts automatically
DoneCrewDeck looks for the next task to start in the same project

A few things to know:

  • The project needs a primary repository. Without one, CrewDeck cannot start the next stage.
  • Only successful runs trigger a follow-up. A task that did not actually leave its stage is not started again.
  • Autonomy also retries failed tasks automatically. A retry is skipped while the project is halted (see Stop on failure).
  • Health checks, agent permissions and capacity queuing still apply to every automatic start.

How the next task is chosen. When a task reaches Done, or when a pull request that another task depended on is merged, CrewDeck picks the next task like this:

  1. Only tasks in the same project that are in To Do are considered.
  2. The task must be assigned to an agent, a command, or command steps.
  3. It must have no unresolved blocking dependencies.
  4. Candidates are taken in board order, top to bottom.

If no task qualifies, nothing starts.

  • The Autonomy halted banner appears: "A task failed while 'Stop on failure' was enabled. Queued tasks are paused until you resume."
  • Automatic retries stop, and every queued start for that project (new tasks, next stages and retries) waits instead of running. Queued work is not lost or marked failed.
  • Other projects keep running.
  • The halt is remembered, so it is still there after you restart CrewDeck.

Nothing is queued after a pause, so a task waiting for your review also stops the "start the next task" chain until you deal with it.

Remote Database​

Remote database keeps a status copy of your work in the cloud so CrewDeck Web can show your board and your history while this Mac is asleep. The section lives in Settings › CloudSync, below the CloudSync panel where you sign in to your account. It is off until you turn it on, and it needs CloudSync switched on with an account linked on this Mac.

Each field in that copy is either readable by the server -- so it can sort, filter, page and count -- or encrypted with your CloudSync key, which the server never holds.

What the server can read

Across your full history of projects, epics, tasks, releases, repos and agents:

  • Task IDs, statuses and stages
  • Priorities and sizes
  • Dates: when items were created, started, updated, completed, published and released
  • Which project, epic or repo each item belongs to
  • Which agents each task is assigned to
  • Release IDs, statuses and pull request numbers
  • Dependency links between tasks and release links to tasks
  • Ciphertext lengths of the encrypted fields

What stays encrypted

Uploaded only as ciphertext, task descriptions included:

  • Project, epic, repo and agent names
  • Task titles and task numbers
  • Task descriptions
  • Release versions, titles and notes

Three things worth knowing

  • It covers your full history, not a recent window. There is no 30-day limit: every task you have ever run is included, apart from workflow-run tasks. How much history fits is governed by your cloud storage quota.
  • Task descriptions are uploaded, encrypted. Each one is capped at 8 KiB in the cloud copy; when you open a task in the browser, the full text is read live from this Mac, which therefore has to be awake.
  • Execution data is never stored in the cloud. Terminal output, run transcripts, command-step output and diffs are read live from this Mac, end-to-end encrypted on the way, and are never kept on the server.

In short: an operator with access to the Remote database can see the shape and cadence of every task you have ever run -- counts, statuses, priorities, sizes, timing, dependency graph, release membership and ciphertext lengths -- though never titles, names, descriptions or notes.

CrewDeck writes a sandbox block into Claude Code's .claude/settings.local.json file when a task begins execution. This block restricts what Claude Code can access on the filesystem, which network domains it may reach, and whether it can run commands outside the sandbox.

Accessing Sandbox Settings

  1. Click the Settings gear in the menu bar
  2. Open the Sandbox & Terminal tab
  3. Find the Terminal Sandbox card

Configurable Policy Fields

SettingDefaultDescription
Denied Directories/etc, /var, ~/.ssh, ~/.awsFilesystem paths Claude Code cannot read or write
Allowed Directories(empty)Additional filesystem paths Claude Code may access beyond the worktree. The worktree path is always auto-included. Tilde (~) paths are expanded at write time.
Allowed Domains(empty)Network domains Claude Code may contact during execution
Unix Sockets~/.ssh/agent-socketUnix socket paths Claude Code may connect to (e.g., for SSH agent operations)
Allow Unsandboxed CommandsOffWhen enabled, allows Claude Code to run commands outside the sandbox constraints

How It Works

When a task execution begins, CrewDeck writes the following structure into the worktree's .claude/settings.local.json:

{
  "permissions": { "...existing..." },
  "sandbox": {
    "enabled": true,
    "allowedDirectories": ["/path/to/worktree", "/additional/path"],
    "deniedDirectories": ["/etc", "/var", "~/.ssh", "~/.aws"],
    "allowedDomains": [],
    "network": { "allowUnixSockets": ["~/.ssh/agent-socket"] },
    "allowUnsandboxedCommands": false
  }
}

The worktree directory is always the first entry in allowedDirectories and is auto-included regardless of user configuration. Any additional paths added in the Allowed Directories setting are merged and deduplicated. Tilde (~) paths are expanded to the user's home directory at write time.

When Execution Completes

The sandbox block is removed from .claude/settings.local.json when the worktree is cleaned up, leaving the file in its original state.

Updating Sandbox Policy

  1. Open Settings → Sandbox & Terminal → Terminal Sandbox
  2. Modify the desired fields:
    • Type a path or domain and click Deny / Allow to add it to the relevant list
    • Click the remove button next to an existing entry to delete it
    • Toggle Allow Unsandboxed Commands on or off
  3. Click Save Policy
  4. The new policy takes effect on the next task execution

Custom Secrets for MCP Servers​

Some MCP servers have their own CrewDeck setup flow. For example, connecting GitHub provisions GH_TOKEN for the GitHub MCP server. For every other server, such as New Relic, store the API key once as a secret and attach it to the server. Do not paste the key into the server's Headers or Config fields.

Creating a Secret​

  1. Go to Settings › AI & Tools › Secrets and click Add Secret
  2. Key: letters, digits and _, not starting with a digit, up to 128 characters (for example NEW_RELIC_API_KEY)
  3. Value: up to 8,192 characters. The value must not contain a ${NAME} placeholder
  4. Description (optional): a note to help you recognise the secret later
  5. Click Add Secret

Rules

  • The value is encrypted on this device and is never shown again. The list shows a fixed •••••••• mask that says nothing about the value's length or content
  • To edit a secret, click Edit on its row. Leave Value blank to keep the stored value, or enter a new value to replace it, then click Save Changes
  • Keys must be unique
  • Names that CrewDeck provisions itself are reserved and rejected: GH_TOKEN, SONAR_API_KEY, CODACY_ACCOUNT_TOKEN, CREWDECK_BASE_BRANCH, CREWDECK_STOP_HOOK_DIR, CREWDECK_NOTIFICATION_HOOK_DIR and CREWDECK_GIT_GUARD_DIR
  • Names that change how a program is found or loaded are rejected: PATH, NODE_OPTIONS, HOME, SHELL, LD_PRELOAD, LD_LIBRARY_PATH and any name starting with DYLD_

Attaching a Secret to an MCP Server (New Relic example)​

  1. In Settings › AI & Tools › MCP Servers, add the server with Server Type http and the MCP endpoint URL from New Relic's documentation, then save it. Secrets can only be attached to a saved server, so click Edit on the server to reopen it
  2. In the server's Secrets area, click Attach Secret
  3. Choose your secret from Select a secret
  4. Enter the target name:
    • For an http server this is the Header name your provider documents. The field suggests Api-Key; use whatever header name New Relic's documentation gives
    • For a stdio server this is the Env var name the server reads, for example NEW_RELIC_API_KEY
  5. Click Save Secrets

Notes

  • A server can carry at most 32 attached secrets
  • The server must be enabled for the project the task runs in. Secrets attached to a server that is not enabled for the project are not passed to that run
  • If your provider needs a prefix, such as Authorization: Bearer <token>, type the header yourself in the server's Headers field as Authorization: Bearer ${NEW_RELIC_API_KEY}. CrewDeck keeps a reference you wrote rather than overwriting it
  • If the target name already holds a literal value, the attachment replaces that value with the reference
  • Host and Content-Length cannot be used as header names
  • Changing the Server Type between stdio and http invalidates existing attachments, because an env var only applies to stdio and a header only applies to http. A mismatched attachment is flagged and skipped at launch. Save the type change, reopen the server, correct the attachment's target name and click Save Secrets

The resulting entry in the worktree's .mcp.json holds only the reference, never the value:

{
  "mcpServers": {
    "new-relic": {
      "type": "http",
      "url": "https://<your-new-relic-mcp-endpoint>",
      "headers": { "Api-Key": "${NEW_RELIC_API_KEY}" }
    }
  }
}

How ${VAR} References Are Resolved​

  1. When a task runs, CrewDeck writes each server entry into the worktree's .mcp.json (and .codex/config.toml for Codex) with ${KEY} references only
  2. For the servers in that run, CrewDeck decrypts each attached value and places it in the agent run's environment
  3. The tool that launches the MCP server replaces each ${KEY} with the matching value from that environment
  • Only CrewDeck's own run environment is used to resolve a reference. Other variables from your shell are never consulted, so an unrelated environment variable cannot be pulled into a server's config
  • A reference that does not match an attached secret is left exactly as written, and the server reports a missing variable or fails to authenticate. A typo in a target name therefore shows up as an authentication failure, not as an error in Settings
  • If the operating system's credential store is unavailable or a value cannot be decrypted, that attachment is skipped with a warning and the run continues without it
  • Values are read again on every run. Nothing is cached between runs beyond the credential store's short-lived cache

Why Values Never Appear in Committed Config​

  • .mcp.json and .codex/config.toml only ever contain ${KEY} references, so committing or sharing them exposes no credential
  • The resolved value lives only in the agent run's environment and in the worktree's local .claude/settings.local.json. CrewDeck adds that file to the worktree's .gitignore, and when CrewDeck commits a run's work it also unstages it, together with .mcp.json and .codex/config.toml, so it does not end up in a commit or pull request. This is the same handling GH_TOKEN already gets
  • The value never comes back to the UI. Settings only ever receives the fixed mask
  • CrewDeck's own log and warning messages name the key or server, never the value
  • Terminal output masks a secret's literal value when it is between 8 and 512 characters long. Shorter or longer values are still passed to the server but are not masked in terminal output

Deleting or Rotating a Secret​

  • To delete a secret, click Delete on its row, then Confirm. The confirmation lists the servers that will lose the credential on their next run. Deleting removes the secret from every server it was attached to
  • Sessions that are already running keep the old value until they are restarted. If a key has leaked, also rotate it at the provider
  • Replacing a value, or attaching a secret to a server, takes effect on the next run

GitHub Token (GH_TOKEN) Setup Is Unchanged​

Connecting GitHub (Device Flow or Personal Access Token in Settings › Integrations) still provisions GH_TOKEN for the GitHub MCP server exactly as before. Custom secrets cannot use GH_TOKEN or any other CrewDeck-provisioned name, cannot override it, and do not change the GitHub server's generated config. Existing GitHub setups need no action.

Export-to-PR Workflow​

Export project data into a GitHub draft pull request using git worktrees, providing a reviewable, version-controlled export path without modifying your working tree.

How It Works

The export-to-PR workflow uses git worktrees to create deterministic exports:

  1. Fetch Latest: Pulls latest changes from remote repository
  2. Default Branch Detection: Automatically detects default branch (main/master) using three-tier fallback
  3. Temporary Worktree: Creates a temporary git worktree with unique branch (export/<type>-YYYY-MM-DD-<nanoid>)
  4. File Export: Writes export files to .crewdeck/shared/export/ directory via callback
  5. Commit & Push: Stages, commits, and pushes changes automatically
  6. Draft PR Creation: Creates a draft PR via gh CLI
  7. Cleanup: Removes the temporary worktree (with fallback to force-delete + prune)

Available Export Types

Export TypeData IncludedAccess Point
Project DataTasks, agents, commands, configurationsSettings → Data & Privacy → Data Export / Import

Exporting to PR

  1. Open Settings → Data & Privacy → Data Export / Import
  2. Click Export to PR as JSON or Export to PR as YAML
  3. Wait for the export process (~10-30 seconds depending on repository size)
  4. A success message displays the PR URL
  5. Click the PR URL link to open it in your default browser
  6. Review the exported files in the PR diff
  7. Merge the PR when ready to share with your team

Export File Structure

All exports write to .crewdeck/shared/export/:

  • project-data.json or project-data.yaml: Full project export

PR Details

Created draft PRs include:

  • Title: Descriptive export type and timestamp
  • Branch Name: export/<type>-YYYY-MM-DD-<unique-id>
  • Status: Draft (requires review before merge)
  • Commit Message: Automated message indicating export source
  • Body: Summary of exported data

Why Worktrees?

Using git worktree add instead of direct file writes provides:

  • Complete isolation from your current work
  • No risk of conflicts with uncommitted changes
  • No need for git stashing
  • Atomic operation — if anything fails, your repo is untouched

Requirements

  • gh CLI: Must be installed and authenticated

    # or download from https://cli.github.com

    # Authenticate
    gh auth login
  • GitHub Token: Must have repo scope with push permissions
  • Primary Repository: Project must have a connected primary repository

Automatic Worktree Cleanup​

CrewDeck creates isolated git worktrees for each task execution. Over time, these worktree folders accumulate and consume disk space. CrewDeck automatically cleans up worktrees when you rate a completed task.

How It Works​

  1. When a task reaches "Done" status, you are prompted to rate it (see Rating Tasks)
  2. After you submit a rating, CrewDeck automatically removes the associated worktree folder
  3. The cleanup is non-blocking -- your rating is saved immediately, and cleanup runs in the background
  4. If cleanup fails (e.g., the worktree was already removed), the failure is logged but does not affect your rating

Cleanup Strategy​

The cleanup process follows a robust approach:

StepAction
1. Find worktreeScans the worktrees directory for the task's manifest file
2. Git removeAttempts git worktree remove --force to properly unregister the worktree
3. FallbackIf git remove fails, directly deletes the folder and runs git worktree prune to clean stale references

Manual Verification​

To verify worktree cleanup, you can check the worktrees directory:

# List active git worktrees
git worktree list

# Check the worktrees folder
ls ~/Library/Application\ Support/crewdeck/worktrees/

Troubleshooting​

"Please connect GitHub in Settings first"​

Cause: GitHub is not authenticated.

Solution:

  1. Click the Settings gear and open the Integrations tab
  2. Use Device Flow (recommended): click Sign in with GitHub, then visit github.com/login/device and enter the displayed code
  3. Alternatively, enter your GitHub Personal Access Token and click Connect GitHub
  4. Ensure the token has the repo scope (PAT method only)

GitHub Device Flow code not accepted​

Cause: The one-time code may have expired (codes are valid for approximately 15 minutes) or was entered incorrectly.

Solution:

  1. Return to Settings in CrewDeck and click Sign in with GitHub again to generate a new code
  2. Visit github.com/login/device promptly and enter the new code
  3. If the problem persists, fall back to Personal Access Token authentication

MCP server fails to authenticate after attaching a secret​

Cause: Any of the following:

  • The attachment was never saved (Save Secrets was not clicked), or it was removed
  • The secret was deleted, or its key was renamed while the server's Headers or Config still contain a ${KEY} reference you typed with the old name, so that reference is left unresolved
  • The server is not enabled for the project the task runs in
  • The Server Type was changed between stdio and http, and the attachment was not re-saved for the new type
  • The session started before the secret was attached or its value was replaced
  • The provider expects a different header or variable name, or a Bearer prefix
  • The operating system's credential store was unavailable, so the attachment was skipped with a warning

Solution:

  1. Open Settings › AI & Tools › MCP Servers, click Edit on the server and check that the secret is listed under Secrets. If not, attach it and click Save Secrets
  2. Check that the secret still exists under Secrets with the expected key
  3. Check that the server is enabled for the project
  4. If you changed the Server Type, save it, reopen the server, correct the flagged attachment and click Save Secrets
  5. Compare the target name with your provider's documentation. For a Bearer scheme, type Authorization: Bearer ${YOUR_KEY} in the server's Headers field
  6. Restart the session, or start a new run, so the current values are picked up

See Custom Secrets for MCP Servers for details.

Agent not found in connected repos​

Cause: The repository may not contain agent definitions, or they weren't discovered.

Solution:

  1. Verify the repo has a .claude/agents/ directory with agent files
  2. Go to Repos tab and click Sync next to the repository
  3. Check the Agents tab to see discovered agents

Solution:

  1. The Agent Execution Mode toggle only appears when 2 or more agents are assigned
  2. Add additional agents to the task to see the toggle
  3. Single-agent tasks always use the standard execution flow

Swarm mode using wrong orchestrator​

Cause: The first selected agent is not an orchestrator type.

Solution:

  1. For best results with swarm mode, select an orchestrator agent (e.g., feature-orchestrator, bugfix-orchestrator) as the first agent
  2. If no orchestrator is detected, CrewDeck defaults to feature-orchestrator
  3. Ensure the default orchestrator exists in your connected repository

Dashboard analytics not loading​

Cause: No task outcomes have been recorded yet, or there is a data loading error.

Solution:

  1. Analytics require completed tasks with recorded outcomes
  2. Complete tasks and provide ratings to populate analytics data
  3. If an error message appears, click the Retry button
  4. Try a different date range to check if data exists for other periods

Agent Intelligence dashboard is empty​

Cause: No agent performance data has been recorded.

Solution:

  1. Agent performance data is populated when tasks complete with outcomes
  2. Run tasks with assigned agents and allow them to complete
  3. Verify that agents are discovered in your project's Agents tab
  4. Check date range filters -- try "All Time" to see all available data

Agent ranking badges not appearing​

Cause: Rankings have not been calculated yet, or agents have insufficient data.

Solution:

  1. Rankings are calculated automatically when task outcomes are recorded
  2. Agents need at least one completed task to receive a ranking
  3. Low-confidence rankings (fewer than 10 tasks) are shown with dashed borders
  4. Open Dashboards → Agent Intelligence & Quality to verify rankings exist

Terminal output not pausing​

Applies to: sessions that show a terminal (CLI and Codex sessions, and terminals you open yourself). SDK sessions show the Activity Panel instead; their Pause execution button asks the agent to stop and save its progress (see Pausing and Cancelling an SDK Session).

Cause: The terminal panel has no manual output-pause control. Output slows down automatically (the Backpressure and Output throttled indicators), and Pause execution pauses the agent, not the output.

Solution:

  1. To stop the agent and save its progress, click Pause execution on the tab of a running session (see Pause and Resume Output)
  2. Completed or failed sessions cannot be paused
  3. If output looks stalled, check the status bar for a Backpressure or Output throttled indicator; delivery resumes on its own

System health blocking session creation​

Cause: CPU or memory usage has reached critical levels.

Solution:

  1. Close or terminate terminal sessions you no longer need
  2. Wait for running tasks to complete
  3. Check the error message for specific resource usage percentages
  4. The message suggests how many sessions to close to free resources
  5. System health refreshes every 30 seconds -- wait and retry

Create New Repo button not working​

Cause: GitHub is not connected, or there are permission issues.

Solution:

  1. Verify GitHub is connected in Settings
  2. Ensure your token has the repo scope for repository creation
  3. Check that the repository name follows GitHub naming rules (no spaces, cannot start with a period)
  4. If the name already exists on your account, choose a different name

Primary/Context repo badges not showing​

Cause: Only one repository is connected to the project.

Solution:

  1. Primary/Context badges only appear when multiple repositories are connected
  2. Connect a second repository to see the badge distinction
  3. The first connected repository is automatically set as primary

Document Wizard not opening​

Cause: The task may not be in the "Document" column.

Solution:

  1. The Document Wizard only activates for tasks in the "Document" column
  2. Ensure the task has been moved to "Document" status
  3. Tasks in other columns use the standard terminal execution flow
  4. Check that the task has a PR link (documentation workflows require a prior PR)

Mark as Failed option not visible​

Cause: The task may already be in "Done" status or has been released.

Solution:

  1. The "Mark as Failed" action is available on active task cards on the Kanban board
  2. Tasks already in "Done" or released status cannot be marked as failed
  3. Look for the warning icon on the task card, or open the task detail view

Telemetry data not recording​

Cause: Telemetry is disabled by default.

Solution:

  1. Open Settings → Data & Privacy → Usage Analytics
  2. Turn on Anonymous Usage Telemetry
  3. Enable specific categories you want to track
  4. Telemetry events are batched and flushed every 30 seconds

Feedback prompts not appearing​

Cause: Feedback prompts are disabled or the workflow category is turned off.

Solution:

  1. Open Settings → Data & Privacy → Feedback
  2. Turn on Feedback Prompts
  3. Prompts appear once per workflow completion -- they do not repeat for the same event

Worktree not cleaned up after rating​

Cause: The worktree may have already been removed, or cleanup encountered an error.

Solution:

  1. Worktree cleanup is non-blocking -- it does not affect your rating
  2. Check if the worktree folder still exists: 
    ls ~/Library/Application\ Support/crewdeck/worktrees/
  3. Manually delete orphaned worktree folders if needed
  4. Run git worktree prune in the source repository to clean stale references

File attachments not visible​

Cause: The attachment may not have been saved correctly, or the file was moved.

Solution:

  1. Verify the file was uploaded by opening the task detail view
  2. Attachments are stored in CrewDeck's local data directory
  3. If the original file was deleted from disk, the attachment link may be broken
  4. Re-attach the file if needed

Auto-update not working​

Cause: Update server may be unreachable, or the app was installed in a read-only location.

Solution:

  1. Ensure you have an internet connection
  2. Restart the application to trigger an update check
  3. Verify the application was installed in a writable location
  4. Check for error notifications regarding update failures
