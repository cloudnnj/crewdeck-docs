Introduction​

What is CrewDeck?​

CrewDeck is a desktop application that enables teams to manage and dispatch work to AI agents. Think of it as a project management tool (like Jira or Trello) specifically designed for AI-powered development workflows.

With CrewDeck, you can:

  • Organize work by team using Projects
  • Connect GitHub repositories to discover AI agents and commands
  • Create tasks on a visual Kanban board
  • Execute tasks with AI agents that write code, create branches, and open Pull Requests
  • Monitor progress in real-time through an integrated terminal

Key Concepts​

ConceptDescription
ProjectA logical grouping for your work — typically representing a team, project, or domain (e.g., "Engineering", "Frontend", "API Team").
RepositoryA GitHub repo connected to a project. Agents and commands are automatically discovered from connected repos.
AgentAn AI specialist that can execute tasks. Examples include "frontend-developer", "code-reviewer", and "database-designer".
CommandA slash command (e.g., /build-feature, /fix-bug) that defines a specific workflow an agent can run.
TaskA work item on the Kanban board. Tasks have a title, description, priority, and can be assigned to agents.
Task NumberA human-readable identifier automatically assigned to each task (e.g., "ENG-0001").
WorktreeA separate working directory for each task. This isolates changes and prevents conflicts with your local development.
ConfigClaude Code configurations including agents, skills, and commands, managed from the Agents, Commands and Skills tabs under Crew in the project header.
SkillA reusable workflow or specialized task automation that extends Claude's capabilities (e.g., /commit, /review-pr).
TemplatePre-built configurations that can be imported into a repository to quickly set up agents, skills, or commands.

Getting Started​

Prerequisites​

Before using CrewDeck, ensure you have:

  1. Node.js 18+ — Download from nodejs.org
  2. Git — Version control system
  3. GitHub Account — For repository integration
  4. GitHub Personal Access Token — With repo scope enabled
  5. Claude Code CLI — The AI agent runtime

Installation​

  1. Download the CrewDeck installer for your platform
  2. Run the installer and follow the on-screen instructions
  3. Launch the CrewDeck application

First-Time Setup​

Step 1: Connect GitHub​

CrewDeck supports two methods for authenticating with GitHub:

Option A: Device Flow (Recommended — new in v0.15.0)

GitHub authentication now supports OAuth Device Flow (RFC 8628), which eliminates port conflicts and does not require a locally running redirect server.

  1. Click Settings in the sidebar (gear icon at the bottom)
  2. In the GitHub Integration section, click Sign in with GitHub
  3. CrewDeck displays a short user code (e.g., ABCD-1234)
  4. Visit github.com/login/device in your browser
  5. Enter the code and authorize CrewDeck
  6. The app detects authorization automatically and shows a green "Connected" status indicator

Option B: Personal Access Token (PAT)

  1. Click Settings in the sidebar (gear icon at the bottom)
  2. In the GitHub Integration section, click the token input field
  3. Go to github.com/settings/tokens and create a Personal Access Token:
    • Click Generate new token (classic)
    • Give it a descriptive name (e.g., "CrewDeck App")
    • Select the repo scope (full control of private repositories)
    • Click Generate token and copy the token
  4. Paste the token into CrewDeck and click Connect GitHub
  5. You should see a green "Connected" status indicator

Step 2: Install Claude Code CLI​

The Claude Code CLI is required to execute tasks with AI agents. In the Settings page, you'll see instructions to install it:

npm install -g @anthropic-ai/claude-code

After installation, verify it works by running claude --version in your terminal.

Step 3: Create Your First Project​

  1. Click the + button next to "Projects" in the sidebar
  2. Enter a name (e.g., "Engineering" or "My Project")
  3. Optionally add a description and choose a color
  4. Click Create Project

Core Workflows​

Project Management​

Projects are the top-level organizational units. Each project has its own:

  • Kanban board with tasks
  • Connected GitHub repositories
  • Discovered agents and commands

Creating a Project​

  1. In the sidebar, click the + button next to "Projects"
  2. Fill in the project details:
    • Name (required): A short identifier (e.g., "Backend", "Mobile")
    • Description (optional): A brief explanation of the project's purpose
    • Color: Choose from 8 preset colors to help visually distinguish projects
  3. Click Create Project

Navigating Projects​

  • Click any project in the sidebar to open it
  • The Dashboard (home icon) shows all projects with their task counts and progress
  • Each project card on the Dashboard displays:
    • Project name and description
    • Total task count
    • Progress bar showing completion percentage

Editing or Deleting a Project​

Currently, projects can be edited or deleted through the project settings. Be cautious when deleting — this removes all associated tasks.

Per-Project Kanban Stage Selection​

Each project can be configured to show only the Kanban columns relevant to its workflow. The two required columns — To Do and Done — are always shown. The three optional columns can be toggled on or off per project.

Optional Stages

StageDefaultWhen to Disable
In ProgressOnSimple projects where tasks go directly from To Do to Done
In ReviewOnProjects without a formal code review step
DocumentOnProjects that don't produce documentation artifacts

Configuring Stages When Creating a Project

  1. Click the + button next to "Projects" in the sidebar
  2. In the Kanban Stages section of the Create Project modal, uncheck any optional stages you don't need
  3. Click Create Project

Configuring Stages for an Existing Project

  1. Open the project and click the project menu (three dots)
  2. Select Edit Project
  3. In the Kanban Stages section, toggle optional stages on or off
  4. Click Save

Display Behavior for Tasks in Disabled Stages

When a stage is disabled, tasks whose database status corresponds to that stage are displayed in the nearest preceding enabled stage. This is a display-only change — the task's actual status in the database is not modified. Re-enabling a stage causes tasks to reappear in their correct columns automatically.

Assigning Claude Accounts to a Project​

Each project can be configured to draw Claude credits from one or more specific stored accounts, so parallel work across projects does not drain a single credit pool — and so that several sessions started at once in the same project do not all queue behind one account's rate limit.

Configuring the Accounts for an Existing Project

  1. Open the project and click the project menu (three dots)
  2. Select Edit Project
  3. In the Claude Account section, tick each account this project should use
  4. Click Save

Behavior

  • No accounts ticked — Follows the account selected in Settings → Claude
  • One account ticked — That account is used for every AI run started from the project, exactly as before
  • Several accounts ticked — Each new agent session is handed the least-busy assigned account, so concurrent work spreads across them instead of stacking on one
  • OAuth-only — The account picker appears only when Claude is authenticated with OAuth
  • Fallback on removal — If an assigned account is later removed, the sessions that would have used it fall back to the default account, and the page shows a warning with a one-click button to drop the stale entries

When an assigned account hits a rate limit, CrewDeck stops sending new sessions to it for a few minutes and may temporarily retry that project's runs with another stored account so work keeps moving. If every assigned account is busy, runs still start — they queue on the least-loaded one rather than failing. The app-wide default account is never changed by any of this.

You can cap how many sessions run on a single account at once, and watch each account's current load, in Settings → Claude.

Account assignment applies to agent sessions that CrewDeck runs for you. Terminal sessions you drive yourself use whatever account the Claude command-line tool is already signed in to.

To add accounts, go to Settings → Claude.

Connecting GitHub Repositories​

To use AI agents, you need to connect at least one GitHub repository that contains agent definitions.

Prerequisites​

  • GitHub must be connected in Settings (see First-Time Setup)
  • You need access to at least one GitHub repository

Connecting a Repository​

  1. Navigate to your project
  2. Click the Repos tab
  3. Browse the list of available repositories from your GitHub account
  4. Click Connect next to the repository you want to add
  5. Wait for the repository to be cloned locally (this may take a moment for large repos)
  6. Once connected, CrewDeck automatically scans for agents and commands

What Gets Discovered​

CrewDeck scans connected repositories for:

DirectoryContentResult
.claude/agents/Agent definition filesAvailable agents appear in the Agents tab
.claude/commands/Command definition filesAvailable commands appear in the Commands tab

Syncing Agents and Commands​

If you update agents or commands in your repository, use the Refresh button to pull changes and re-discover configurations:

  1. Go to the Repos tab in CrewDeck
  2. Click the Refresh button (circular arrow icon) next to the repository
  3. CrewDeck will:
    • Pull the latest changes from the remote repository
    • Re-scan for agents and commands
    • Update the agent/command lists automatically

Refresh Button Behavior

Repository TypeAction
Primary/Context ReposPulls latest, re-discovers agents and commands
Marketplace ReposPulls latest, re-discovers marketplace agents

Error Handling

The refresh operation may fail in certain situations:

An error banner displays with specific instructions when refresh fails. Click the X to dismiss it.

Disconnecting a Repository​

  1. Go to the Repos tab
  2. Click Disconnect next to the repository you want to remove

Creating a New Repository​

Primary and Context Repositories​

When a project has multiple connected repositories, CrewDeck distinguishes between them using primary and context designations.

How It Works

DesignationDescription
PrimaryThe main working repository where code changes happen. The first connected repo is automatically set as primary. Shown with a blue "Primary" badge.
ContextAdditional repositories that provide supplementary documentation. Shown with a purple "Context" badge when multiple repos are connected.

Context repos contribute documentation from their docs/ folders and PROJECTS.md files to enhance AI-generated agent and command suggestions in the Generate wizard on the Agents, Commands and Skills tabs.

Changing the Primary Repository

  1. Navigate to the Repos tab
  2. Find the context repository you want to make primary
  3. Click the Set Primary button
  4. The previous primary becomes a context repository
  5. Context caches are automatically refreshed

Context in Config Generation

When using the Generate wizard on the Agents, Commands or Skills tab:

  1. CrewDeck automatically fetches documentation from context repos
  2. A purple indicator shows "Context available from N connected repos"
  3. This context is included in the AI generation prompt for more relevant suggestions

Alternative Branching Strategies​

By default, CrewDeck creates feature branches from the repository's default branch (usually main). Starting in v0.12.0, you can configure per-project branching strategies to match your team's workflow.

Supported Strategies

StrategyDescriptionBranch Pattern
DefaultFeature branches from the default branchfeature/{task-slug}-{id}
Trunk-BasedShort-lived branches from main or trunkfeature/{task-slug}-{id}
GitFlowFeature branches from develop, releases from release/feature/{task-slug}-{id} from develop
CustomUser-defined base branch per projectConfigurable

Configuring a Branching Strategy

  1. Navigate to your project's Settings or Repos tab
  2. Select the branching strategy for the project
  3. For custom strategies, specify the base branch name
  4. All new task executions will use the configured strategy

How It Works

  • When a task starts execution, the worktree is created from the configured base branch instead of the default branch
  • PR targets are automatically set to the correct base branch
  • Existing tasks with worktrees are not affected by strategy changes

Natural Language Task Creation​

CrewDeck can extract structured task details from natural language descriptions using AI, eliminating the need to manually fill in each form field.

How to Use

  1. Click Add Task on the Kanban board
  2. Click the From Description tab in the Create Task modal
  3. Describe your task in natural language in the text area (up to 5,000 characters)
    • Example: "We need to build a user authentication system with JWT tokens, password hashing using bcrypt, and email verification. This should work with our PostgreSQL database and include rate limiting for login attempts."
  4. Click Extract & Fill Form
  5. Wait for AI to analyze your description (~5-15 seconds)
  6. Review the auto-populated fields:
    • Title: Concise imperative form (max 80 characters)
    • Description: 2-3 sentence summary with acceptance criteria as a markdown checklist
    • Priority: Assigned based on urgency and impact indicators
    • Agents: Automatically matched to your project's available agents
    • Confidence Score: Shows AI's confidence in the extraction quality
  7. Edit any fields as needed
  8. Click Create Task

What Gets Extracted

FieldHow It's Determined
TitleAI condenses description into an actionable task title
DescriptionAI rewrites as a clear summary with checklist acceptance criteria
PriorityAssigned based on keywords like "urgent", "critical", "nice-to-have"
Suggested AgentsMatched against your project's agents using name normalization
Confidence0-100% score indicating extraction quality

Graceful Fallback

If extraction fails (timeout, network error, or AI returns invalid JSON):

  • Click Continue Manually to proceed with your original description pre-filled
  • Your description is never lost — it's preserved in the form
  • You can retry extraction or continue filling fields manually

Tips for Best Results

  • Include specific requirements, not just vague goals
  • Mention technology stack or frameworks to help with agent matching
  • Use urgency keywords for automatic priority assignment
  • Keep descriptions focused on a single task (not multiple unrelated items)

Auto-Task Decomposition​

Break down large epics or complex tasks into smaller, actionable subtasks automatically using AI.

When to Use

  • You have a large task that represents multiple smaller work items
  • You want to parallelize work across multiple agents
  • You need to establish dependencies between related subtasks
  • You want AI to suggest optimal task sequencing

How to Use

  1. Create or select a task in the "To Do" column that represents an epic
  2. Click on the task to open the detail view
  3. Click the Auto-decompose button
  4. Wait for AI analysis (~15-30 seconds)
  5. Review the suggested subtasks in the Decompose Task modal:
    • Each subtask shows title, description, priority, suggested agents, commands, and dependencies
    • Confidence scores indicate AI's certainty about each subtask
    • Color-coded badges show confidence levels (green ≥70%, yellow ≥40%, red <40%)
  6. Select which subtasks to create (use Select All / Deselect All toggles)
  7. Edit any subtask details inline:
    • Modify titles or descriptions by clicking on them
    • Adjust priorities using the dropdown
  8. Click Create Selected Tasks
  9. Wait for subtask creation and dependency wiring
  10. Optionally rate the decomposition quality (1-5 stars) to improve future suggestions

What AI Analyzes

The decomposition service considers:

  • The parent task title and description
  • Your project's available agents and commands
  • Historical patterns from similar tasks (via cross-task learning)
  • Best practices for task sequencing and parallelization

Automatic Dependency Wiring

After creation:

  • Inter-subtask dependencies: AI-suggested dependencies between subtasks (e.g., "Build API" must complete before "Build UI")
  • Parent-child blocking: Each subtask automatically blocks the parent epic until all subtasks complete
  • DAG validation: Circular dependencies are prevented

Configuration

Up to 20 subtasks can be generated per decomposition (configurable limit). The AI prefers fan-out/parallel patterns over linear chains to maximize parallelization opportunities.

Quality Feedback Loop

After creating subtasks, you can rate the decomposition quality:

  • 1-5 star rating
  • Optional comment for specific feedback
  • Metrics tracked: subtasks generated, accepted, and modified
  • This data improves future decomposition suggestions

Epics​

Epics are high-level containers that group related tasks under a shared parent theme or source document. They provide a way to organize work that conceptually belongs together — such as all tasks derived from a product requirement document or a strategic initiative — without requiring each task to be a direct child in a strict hierarchy.

Creating an Epic

  1. Navigate to your project's Board tab
  2. Click Add Task and fill in the task details as usual
  3. In the task creation form, enable the Epic toggle
  4. Provide a descriptive title that captures the parent theme (e.g., "Authentication Overhaul", "Q1 Performance Initiative")
  5. Click Create Task — the new task is marked as an epic with a distinct badge on the Kanban board

Auto-Decomposing an Epic into Subtasks

Epics can be automatically decomposed into a set of actionable subtasks using the same AI decomposition engine described in Auto-Task Decomposition:

  1. Open the epic task from the Kanban board
  2. Click Auto-decompose in the task detail view
  3. Review the AI-generated subtasks in the Decompose Task modal
  4. Select which subtasks to create and click Create Selected Tasks
  5. Each created subtask is automatically linked to the epic as a child

Epic Badge and Progress

Epic tasks display a dedicated badge on the Kanban card and in the task detail view:

ElementDescription
Epic badgePurple "Epic" label distinguishing it from standard tasks
Child countShows how many subtasks belong to this epic
Progress barProportion of child tasks in "Done" status out of total children

Linking Existing Tasks to an Epic

You can associate existing tasks with an epic after creation:

  1. Open the task you want to link
  2. In the task detail view, find the Epic field
  3. Select the parent epic from the dropdown
  4. Click Save — the task now counts toward the epic's progress

When to Use Epics

  • Decomposing a large feature specification or product requirements document into parallel workstreams
  • Grouping all tasks related to a single GitHub Issue or roadmap item
  • Coordinating multi-team work where each subtask is owned by a different agent or developer
  • Tracking high-level initiative progress on the Kanban board without losing granular task detail

Epic Filter Pills — Conditional Visibility

The Kanban board header displays epic filter pills so you can narrow the board to tasks belonging to a single epic. Filter pills only appear for epics that have at least one task currently visible on the board:

  • Epics from past development cycles whose tasks are all released, failed, or deleted are automatically hidden from the filter bar
  • If the currently selected epic filter becomes inactive (all its tasks disappear from the board), the filter resets to "All" automatically
  • Epic badges on individual task cards continue to show the epic name regardless of filter visibility

Task Numbers​

Each task automatically receives a unique task number based on the project name:

  • Format: ABC-0001, ABC-0002, etc.
  • The prefix is derived from the project name (e.g., "Engineering" → "ENG")
  • Task numbers are sequential within each project

Editing Tasks​

  1. Click on a task card to open the detail view
  2. Modify the fields you want to change
  3. Click Save

Note: Tasks can only be edited when in the "To Do" status. Once a task moves to "In Progress", it becomes read-only.

Moving Tasks Between Columns​

  • Drag and drop: Click and hold the drag handle on a task card, then drag it to another column
  • Tasks automatically update their status when moved to a new column
  • Moving a task to "In Progress" does not automatically start execution — you need to click Run

Deleting Tasks​

  1. Click the Delete button (trash icon) on the task card
  2. Confirm the deletion when prompted

Task Dependencies​

CrewDeck supports a comprehensive task dependency system that allows you to define prerequisite relationships between tasks, ensuring work happens in the correct order.

Dependency Types

TypeBehaviorUse Case
BlocksHard blocker — dependent task cannot start until this task completesCritical prerequisites (e.g., "API endpoints must be built before UI")
RequiresInformational — indicates the task needs output from another task but doesn't block executionSoft dependencies for awareness (e.g., "UI should use API patterns")
RelatedContextual relationship — shows tasks are related without blockingGrouping related work for visibility

Adding Dependencies

When creating a new task:

  1. In the Create Task modal, scroll to the Dependencies section
  2. Click Add Dependency
  3. Search for the task(s) this new task depends on
  4. Select the dependency type (Blocks, Requires, or Related)
  5. Add multiple dependencies as needed
  6. CrewDeck validates that no circular dependencies are created

When editing an existing task (in "To Do" status):

  1. Open the task detail view
  2. Navigate to the Dependencies section
  3. Click Edit Dependencies
  4. Add or remove dependencies as needed

Viewing Dependencies

Task cards display a dependency badge showing:

  • Amber badge: Task has unresolved blocking dependencies (cannot be started)
  • Gray badge: All blocking dependencies are resolved (task is ready)
  • Count: Number shown indicates total dependencies

In the task detail view, you can see:

  • Depends On: Tasks this task depends on (with status indicators)
  • Required By: Tasks that depend on this task (reverse lookup)

Dependency Enforcement

The dependency system enforces constraints at multiple layers:

  • UI: You cannot drag a task with unresolved blocking dependencies to "In Progress"
  • Backend: API calls to start tasks with unresolved blocking dependencies are rejected
  • Database: Circular dependencies are detected and prevented using DAG validation

Circular Dependency Prevention

CrewDeck automatically detects circular dependencies using a recursive database query:

  • If adding a dependency would create a cycle (A depends on B, B depends on A), the operation is rejected
  • This validation runs for all dependency types, not just "blocks"
  • Maximum dependency chain depth is limited to 100 levels for safety

Auto-Chaining for Generated Tasks

When you use the Generate Tasks or Dispatch Tasks features:

  • Tasks are automatically linked with sequential "blocks" dependencies
  • Task 2 depends on Task 1, Task 3 depends on Task 2, etc.
  • This creates an automatic execution pipeline for batch-generated work

AI-Driven Dependency Suggestions

CrewDeck can automatically suggest dependencies based on task content and project context. This feature uses AI to analyze task descriptions and recommend which tasks should depend on others, helping you build accurate dependency graphs without manual analysis.

Example Workflows

Frontend/Backend Split:

  • Task A: "Build API endpoints" (no dependencies)
  • Task B: "Build UI components" (blocks on Task A)
  • Result: UI work cannot start until API is complete

Parallel Work with Final Integration:

  • Task A: "Design database schema" (no dependencies)
  • Task B: "Build auth service" (blocks on Task A)
  • Task C: "Build user service" (blocks on Task A)
  • Task D: "Integration testing" (blocks on Task B and Task C)
  • Result: Tasks B and C can run in parallel after A completes; D waits for both

Saving a Task as Template

  3. Name your template
  4. Optionally add a category (backend, frontend, bugfix, etc.)
  5. Define variables by replacing specific values with {{variable_name}} placeholders
  6. Click Save Template

Managing Templates

Access template management from the Project page Crew → Templates tab:

  • Browse 12 built-in starter templates covering common development tasks

VCS-Driven Task Templates​

Task templates can be stored directly in your repository's version control system, enabling teams to share and evolve templates alongside their codebase.

How It Works

When VCS-driven templates are enabled, CrewDeck reads template definitions from a designated directory in the primary repository:

.crewdeck/

Task Intelligence and Semantic Search​

CrewDeck includes an AI-powered task intelligence system that generates semantic embeddings for tasks and enables similarity-based search to find related work.

What are Task Embeddings?

Task embeddings are 768-dimensional vector representations of your task titles and descriptions. They capture the semantic meaning of tasks, allowing the system to find conceptually similar tasks even when they use different wording.

Generating Embeddings

Task embeddings are generated automatically in the background using a local Ollama model (nomic-embed-text). No external API keys are required — the system runs entirely on your local machine.

  1. Ensure Ollama is running locally with the nomic-embed-text model pulled
  2. Embeddings are generated automatically when tasks are created or updated
  3. Embeddings are cached locally in SQLite

Finding Similar Tasks

Use semantic search to find tasks related to your current work:

  1. Open any task detail view
  2. Click Find Similar Tasks
  3. The system searches for tasks in the same project with high similarity scores
  4. Results show similarity percentages and highlight conceptually related work

Similarity Scoring

  • Cosine similarity algorithm compares embedding vectors
  • Minimum similarity threshold: 30%
  • Only compares tasks within the same project
  • Results ranked by relevance (highest similarity first)

Keyword Fallback

If Ollama is unavailable, the system automatically falls back to TF-based (term frequency) keyword matching:

  • Tokenizes task text and removes stop words
  • Computes term frequencies
  • Maps to a 100-dimensional keyword vector
  • Provides basic similarity search without local model dependency

Circuit Breaker Protection

The system includes a circuit breaker to prevent cascading failures:

  • Closed: Normal Ollama operation
  • Open: After 3 consecutive failures, switches to keyword fallback for 60 seconds
  • Half-Open: After cooldown, tries one Ollama call. Success closes circuit; failure reopens it

Use Cases

  • Find previous tasks that solved similar problems
  • Identify duplicate or overlapping work
  • Discover related tasks for dependency planning
  • Build context when starting new tasks

Privacy & Security

  • Embeddings generated locally via Ollama — no data sent to external APIs
  • Embeddings cached locally in SQLite
  • Expired embeddings automatically cleaned up after TTL

Pause and Resume Task Execution​

CrewDeck allows you to pause long-running task executions and resume them later, preserving the Claude CLI conversation context.

Pausing a Running Task

  1. Locate a task with an active running session (look for the session indicator on the task card)
  2. Click the amber Pause button (⏸) next to the session indicator
  3. A confirmation dialog appears asking you to confirm the pause — this prevents accidental interruption of long-running agent work (see Terminal Session Confirmation Dialogs)
  4. Confirm the pause to gracefully terminate the PTY process and save the execution state
  5. The task shows a "Paused" indicator with the pause timestamp

What Gets Saved

When you pause a task, CrewDeck saves:

  • Claude CLI session ID for resume capability
  • Current command chain position (if using command chaining)
  • Execution phase at time of pause
  • Assigned agent IDs
  • Worktree path and branch name

This state is persisted to a .crewdeck-pause-state.json file in the task's worktree.

Resuming a Paused Task

  1. Locate the paused task (it will show an amber "Paused" badge)
  2. Click the Resume button (▶)
  3. CrewDeck spawns a new terminal session and attempts to resume using Claude CLI's --resume flag
  4. If a session ID is available, it runs: claude --resume "<session-id>"
  5. If no session ID is found, it uses: claude --continue to continue from the last checkpoint

Resume Behavior

  • The resumed session picks up where the paused session left off
  • Claude maintains conversation context across the pause/resume cycle
  • Terminal output continues in a new session
  • If resume fails, the pause state is restored so you can try again

Use Cases

  • Resource management: Pause tasks to free up terminal sessions for higher-priority work
  • Work breaks: Pause long-running tasks during breaks without losing context
  • Session limits: Manage concurrent session limits by pausing lower-priority tasks
  • Context preservation: Keep Claude's conversation state across application restarts

Session Resume​

In addition to pausing and resuming the current task, CrewDeck supports resuming a specific previous Claude CLI session by ID. This is useful when you want to return to an earlier session that was not paused through the standard flow.

Using Session Resume

  1. Open the terminal panel for a task that has an existing worktree
  2. Click the Resume Session button in the terminal toolbar
  3. A session picker dialog appears listing recent Claude CLI sessions associated with this task
  4. Select the session you want to resume
  5. CrewDeck spawns a new PTY with claude --resume "<session-id>"
  6. Claude restores the conversation context from the selected session

When to Use Session Resume

  • Application restart: Resume a session that was running before CrewDeck was restarted
  • Crash recovery: Pick up a session that was interrupted by a crash or system sleep
  • Exploratory work: Return to a previous session to try a different approach

Sleep Prevention​

CrewDeck automatically prevents your computer from going to sleep while active terminal sessions are running, ensuring long-running AI agent tasks are not interrupted.

How It Works

Sleep prevention activates automatically using Electron's built-in powerSaveBlocker API:

  • Automatic activation: When the first terminal session spawns (interactive or task execution)
  • Reference counting: Sleep prevention stays active as long as at least one session is running
  • Automatic deactivation: When the last terminal session exits or is killed
  • Cross-platform: Works on macOS, Windows, and Linux

Blocker Type

CrewDeck uses the prevent-app-suspension blocker type:

  • System sleep: Prevented — your machine stays awake
  • Display sleep: Allowed — your screen can turn off to save power
  • Background operation: Enabled — sessions continue running even with display off

Manual Control

You don't need to manually run caffeinate or adjust system settings. Sleep prevention is fully automated based on terminal session lifecycle.

Status Visibility

While sleep prevention doesn't have a visible indicator in the UI, you can verify it's active by checking:

  • System settings show the application preventing sleep
  • macOS Activity Monitor shows CrewDeck preventing idle sleep
  • Your system won't go to sleep automatically during active agent execution

Clean Shutdown

Sleep prevention is forcefully stopped when:

  • You quit CrewDeck
  • All terminal sessions are terminated
  • The application is restarted

App Refresh Protection​

CrewDeck prevents accidental renderer refreshes (Cmd+R, Ctrl+R, F5) when active terminal sessions exist, protecting you from losing running AI agent work and wasted Claude API tokens.

Two-Layer Defense

CrewDeck uses defense-in-depth with independent safety layers:

Layer 1: Main Process Interception (Primary)

  • Intercepts keyboard shortcuts: Cmd+R, Ctrl+R, Cmd+Shift+R, Ctrl+Shift+R, F5
  • Queries active terminal session count
  • Shows a native confirmation dialog when sessions are running
  • Dialog displays:
    • Warning icon and session count
    • Risk explanation (API token waste, task interruption)
    • "Cancel" (default) and "Refresh Anyway" buttons
  • Allows normal refresh when no sessions are active

Layer 2: Renderer beforeunload Handler (Secondary)

  • Catches edge cases like programmatic refreshes or browser-triggered navigation
  • Checks Zustand store for running sessions
  • Calls preventDefault() to trigger browser warning prompt
  • Only activates when running sessions exist

User Experience

ScenarioBehavior
Cmd+R with 0 sessionsRefreshes normally without prompt
Cmd+R with 1+ sessionsNative dialog shows warning, blocks refresh by default
User clicks "Cancel"Page stays loaded, sessions continue running
User clicks "Refresh Anyway"Page reloads (explicit confirmation)
F12, Zoom shortcutsStill work normally (not intercepted)

Why This Matters

Accidental refreshes during AI agent execution:

  • Destroy WebContents sender references, orphaning PTY sessions
  • Waste Claude API tokens from interrupted mid-task processing
  • Lose session state (although reconnection exists as a safety net)

Terminal Sandboxing

As of v0.13.0, all renderer windows run in Electron sandbox mode (sandbox: true). Refresh protection now also accounts for the sandboxed renderer context: if the renderer is compromised or in an unexpected state, the main-process interception layer (Layer 1) continues to function independently, maintaining protection even when the renderer beforeunload handler cannot fire.

Dialog Behavior

  • Only one dialog shown at a time (prevents stacking from rapid key presses)
  • Native dialog blocks event loop (appropriate for critical confirmation)
  • Works even if renderer is in a bad state
  • Session count checked at time of keypress (TOCTOU consideration: if sessions complete while dialog is open, refreshing is harmless)

The PR Watcher scans a project's open pull requests on a schedule, auto-merges the eligible ones and dispatches fix agents for failing checks. Its settings live in Settings → Autonomy → PR Watcher; the poll-mode controls appear once the watcher is enabled for the project.

Poll modes

ModeWhat drives scans
Poll (default)An interval scan every 5 minutes (or the project's configured interval, never faster than 30 seconds)

Fallback rule. Hybrid and Webhook need an active webhook subscription for the project's primary repository. Capability-Based Agent Permissions​

As of v0.13.0, marketplace agents declare a set of capabilities in their manifest. CrewDeck enforces these declarations to constrain what each agent is permitted to do during task execution.

How Capabilities Work

Each agent manifest includes a capabilities array:

# .claude/agents/frontend-developer.yml
name: frontend-developer
capabilities:
  - file:read
  - file:write
  - shell:run-tests
  - github:create-pr

When an agent attempts an action not listed in its capabilities, the operation is blocked and the agent receives an error response. This limits the blast radius if an agent behaves unexpectedly or is compromised.

Cross-Task Learning​

CrewDeck automatically learns from completed task executions and enriches new task prompts with relevant historical patterns, enabling AI agents to improve over time.

How It Works

Cross-task learning operates in two phases:

Phase 1: Extraction (on task completion)

When a task transitions to "done" status:

  1. Fetches task details, outcome, agents, commands, and terminal output
  2. Builds structured patterns (agent configuration, command sequences, execution mode, duration)
  3. Extracts error/resolution pairs from terminal output via regex heuristics
  4. Extracts key decisions from agent trace events
  5. Calculates a quality score (0-100) based on outcome status, user rating, and error count
  6. Stores the learning with upsert semantics (one learning per task)
  7. Ensures an embedding exists for semantic similarity matching

Phase 2: Injection (before task execution)

When a task is about to execute:

  1. Checks if cross-task learning is enabled (feature flag in settings)
  2. Uses 500ms timeout-protected query to fetch relevant learnings
  3. Finds semantically similar tasks via TaskIntelligenceService
  4. Filters learnings by project scope, minimum similarity (0.4), and minimum quality (30)
  5. Formats top 3 learnings as markdown with agent config, commands, errors, decisions, and outcome
  6. Appends the formatted context to the task description before passing to AI agent

Learning Data Structure

Each learning captures:

FieldDescription
PatternsAgent IDs/names, command info, execution mode, duration, outcome status
Error ResolutionsError/resolution pairs extracted from terminal output (max 10 pairs)
Key DecisionsDecisions from agent trace events (description, phase, confidence)
Output SummaryTruncated terminal output (max 10KB) with priority retention (first 20% + last 80%)
Quality Score0-100 score based on outcome, user rating, and error count

Quality Scoring Algorithm

Base score:
  success  → 80
  partial  → 50
  failure  → 20
  unknown  → 20

User rating bonus (if rated 1-5):
  bonus = (rating - 3) * 5    // Range: -10 to +10

Error penalty:
  penalty = min(10, errorCount * 2)

Final = clamp(base + bonus - penalty, 0, 100)

Enabling Cross-Task Learning

  1. Navigate to Settings → Advanced → Cross-Task Learning
  2. Toggle the Enable Cross-Task Learning switch
  3. Learnings are extracted regardless of this setting (only injection is gated)
  4. Disable if you notice prompt pollution or want to test agent behavior without historical bias

Similarity Matching

The service uses TaskIntelligenceService embeddings to find relevant historical learnings:

  • Minimum similarity threshold: 0.4 (40%)
  • Minimum quality threshold: 30 (out of 100)
  • Maximum results: 3 learnings per prompt
  • Project-scoped: Only learnings from the same project are considered

Formatted Learning Context

Learnings are injected into task descriptions as markdown:

## Historical Learnings from Similar Tasks

### Learning 1: <Task Title> (Similarity: 85%)

**Errors Encountered**:
- `ECONNREFUSED: Connection refused` → Resolved by starting PostgreSQL service
- `Module not found: bcrypt` → Resolved by running npm install bcrypt

**Key Decisions**:
- Used JWT tokens instead of session cookies for better scalability
- Implemented rate limiting at middleware level

---

Fire-and-Forget Extraction

Learning extraction is non-blocking to avoid slowing down task completion:

  • Runs in background with Promise.catch() only
  • Task update succeeds even if extraction fails
  • Errors are logged but don't interrupt the workflow

Timeout-Protected Injection

Learning injection never delays task execution:

  • Uses Promise.race with 500ms timeout
  • If similarity query takes too long, task proceeds without historical context
  • Prevents blocking the critical path for task execution

Use Cases

  • Error Prevention: Avoid repeating resolved errors from past tasks
  • Best Practices: Propagate successful patterns and agent configurations
  • Decision Guidance: Surface key decisions that led to good outcomes
  • Efficiency: Reduce trial-and-error by learning from historical data

Privacy & Scoping

  • Learnings are project-scoped (no cross-project contamination)
  • Terminal output is truncated to prevent sensitive data leakage
  • Stored in local SQLite database (not shared externally)
  • Disable feature entirely via settings if needed

Agent Intelligence and your data (ADR-0026)

Agent Memory and Cross-Task Learning are pinned to local AI processing. Extraction and similarity matching for both features run entirely on your local Ollama model — task content, terminal output, and stored memory or learning entries are never sent to a cloud AI provider (Anthropic, OpenAI, Gemini, or xAI), regardless of which provider you have selected elsewhere in CrewDeck.

This is enforced in code, not just by convention: a privacy-pinned prompt that resolves to any non-Ollama provider is refused and routed to the local model instead. If Ollama is unavailable, extraction is skipped rather than retried remotely.

Event Sourcing​

CrewDeck implements an event sourcing pattern to maintain a complete, immutable audit trail of all state changes in the system.

What is Event Sourcing?

Event sourcing captures every state change as an append-only event in the state_events table. Instead of just storing current state, the system records every transition, allowing you to:

  • Replay history to reconstruct past states
  • Audit all changes for compliance and debugging
  • Analyze patterns in how tasks and agents evolve over time

What Events Are Captured

The system tracks events for:

  • Tasks: Created, updated status, assigned agents, dependencies added
  • Agents: Discovered, updated, removed
  • Releases: Created, updated, published
  • Terminals: Session started, output written, session ended
  • All other entities: Any state mutation triggers an event

Event Structure

Each event includes:

  • Entity type: What was changed (task, agent, release, etc.)
  • Entity ID: Which specific instance was changed
  • Action: What happened (created, updated, deleted, etc.)
  • Previous state: Snapshot of data before the change
  • New state: Snapshot of data after the change
  • Metadata: Additional context (user ID, timestamp, etc.)
  • Timestamp: When the event occurred

Viewing Event History

Access event history through the API:

// Get all events for a specific task
const events = await window.api.events.getByEntity('task', taskId)

// Filter events by action type
const events = await window.api.events.list({ action: 'task:updated' })

// Count events in a time range
const count = await window.api.events.count({ startDate, endDate })

Event Retention

  • Events are retained for 90 days by default
  • Cleanup runs automatically to remove expired events
  • Maximum 1 million events stored at any time
  • Old events are deleted in batches to avoid blocking

Performance Optimizations

  • Deferred writes: Events are batched using setImmediate() to avoid blocking the event loop
  • Single transactions: Batched events are written in one transaction for efficiency
  • Emergency flush: If more than 10,000 events are pending, emergency batch writes are triggered
  • Sensitive data filtering: Fields like passwords and API keys are automatically stripped from snapshots

Use Cases

  • Debugging: Replay events to understand how a task reached its current state
  • Compliance: Maintain audit trails for regulated environments
  • Analytics: Analyze patterns in task state transitions
  • Conflict resolution: Understand conflicting changes in collaborative scenarios
  • Time travel: Reconstruct system state at any point in the past

Architecture

The event sourcing system uses a Change Data Capture pattern:

  • Entity tables (tasks, agents) remain the source of truth
  • State changes are written to entity tables as normal
  • Events are recorded in parallel to state_events as an audit log
  • Events never modify entities; they are append-only records

Automatic Worktree Cleanup​

CrewDeck creates isolated git worktrees for each task execution. Over time, these worktree folders accumulate and consume disk space. CrewDeck automatically cleans up worktrees when you rate a completed task.

How It Works​

  1. When a task reaches "Done" status, you are prompted to rate it (see Rating Tasks)
  2. After you submit a rating, CrewDeck automatically removes the associated worktree folder
  3. The cleanup is non-blocking -- your rating is saved immediately, and cleanup runs in the background
  4. If cleanup fails (e.g., the worktree was already removed), the failure is logged but does not affect your rating

Cleanup Strategy​

The cleanup process follows a robust approach:

StepAction
1. Find worktreeScans the worktrees directory for the task's manifest file
2. Git removeAttempts git worktree remove --force to properly unregister the worktree
3. FallbackIf git remove fails, directly deletes the folder and runs git worktree prune to clean stale references

Manual Verification​

To verify worktree cleanup, you can check the worktrees directory:

# List active git worktrees
git worktree list

# Check the worktrees folder
ls ~/Library/Application\ Support/crewdeck/worktrees/

Remote Database​

Remote database keeps a status copy of your work in the cloud so CrewDeck Web can show your board and your history while this Mac is asleep. The section lives in Settings › CloudSync, below the CloudSync panel where you sign in to your account. It is off until you turn it on, and it needs CloudSync switched on with an account linked on this Mac.

Each field in that copy is either readable by the server -- so it can sort, filter, page and count -- or encrypted with your CloudSync key, which the server never holds.

What the server can read

Across your full history of projects, epics, tasks, releases, repos and agents:

  • Task IDs, statuses and stages
  • Priorities and sizes
  • Dates: when items were created, started, updated, completed, published and released
  • Which project, epic or repo each item belongs to
  • Which agents each task is assigned to
  • Release IDs, statuses and pull request numbers
  • Dependency links between tasks and release links to tasks
  • Ciphertext lengths of the encrypted fields

What stays encrypted

Uploaded only as ciphertext, task descriptions included:

  • Project, epic, repo and agent names
  • Task titles and task numbers
  • Task descriptions
  • Release versions, titles and notes

Three things worth knowing

  • It covers your full history, not a recent window. There is no 30-day limit: every task you have ever run is included, apart from workflow-run tasks. How much history fits is governed by your cloud storage quota.
  • Task descriptions are uploaded, encrypted. Each one is capped at 8 KiB in the cloud copy; when you open a task in the browser, the full text is read live from this Mac, which therefore has to be awake.
  • Execution data is never stored in the cloud. Terminal output, run transcripts, command-step output and diffs are read live from this Mac, end-to-end encrypted on the way, and are never kept on the server.

In short: an operator with access to the Remote database can see the shape and cadence of every task you have ever run -- counts, statuses, priorities, sizes, timing, dependency graph, release membership and ciphertext lengths -- though never titles, names, descriptions or notes.

Sandbox Security Policy Configuration​

CrewDeck writes a sandbox block into Claude Code's .claude/settings.local.json file when a task begins execution. This block restricts what Claude Code can access on the filesystem, which network domains it may reach, and whether it can run commands outside the sandbox.

Accessing Sandbox Settings

  1. Click Settings in the sidebar
  2. Navigate to the Security tab
  3. Scroll to the Terminal Sandbox section

Configurable Policy Fields

SettingDefaultDescription
Denied Directories/etc, /var, ~/.ssh, ~/.awsFilesystem paths Claude Code cannot read or write
Allowed Directories(empty)Additional filesystem paths Claude Code may access beyond the worktree. The worktree path is always auto-included. Tilde (~) paths are expanded at write time.
Allowed Domains(empty)Network domains Claude Code may contact during execution
Unix Sockets~/.ssh/agent-socketUnix socket paths Claude Code may connect to (e.g., for SSH agent operations)
Allow Unsandboxed CommandsOffWhen enabled, allows Claude Code to run commands outside the sandbox constraints

How It Works

When a task execution begins, CrewDeck writes the following structure into the worktree's .claude/settings.local.json:

{
  "permissions": { "...existing..." },
  "sandbox": {
    "enabled": true,
    "allowedDirectories": ["/path/to/worktree", "/additional/path"],
    "deniedDirectories": ["/etc", "/var", "~/.ssh", "~/.aws"],
    "allowedDomains": [],
    "network": { "allowUnixSockets": ["~/.ssh/agent-socket"] },
    "allowUnsandboxedCommands": false
  }
}

The worktree directory is always the first entry in allowedDirectories and is auto-included regardless of user configuration. Any additional paths added in the Allowed Directories setting are merged and deduplicated. Tilde (~) paths are expanded to the user's home directory at write time.

When Execution Completes

The sandbox block is removed from .claude/settings.local.json when the worktree is cleaned up, leaving the file in its original state.

Updating Sandbox Policy

  1. Open the Sandbox Settings panel in Settings > Security > Terminal Sandbox
  2. Modify the desired fields:
    • Type a path or domain and click Deny / Allow to add it to the relevant list
    • Click the remove button next to an existing entry to delete it
    • Toggle Allow Unsandboxed Commands on or off
  3. Click Save Policy
  4. The new policy takes effect on the next task execution

Custom Secrets for MCP Servers​

Some MCP servers have their own CrewDeck setup flow. For example, connecting GitHub provisions GH_TOKEN for the GitHub MCP server. For every other server, such as New Relic, store the API key once as a secret and attach it to the server. Do not paste the key into the server's Headers or Config fields.

Creating a Secret​

  1. Go to Settings › AI & Tools › Secrets and click Add Secret
  2. Key: letters, digits and _, not starting with a digit, up to 128 characters (for example NEW_RELIC_API_KEY)
  3. Value: up to 8,192 characters. The value must not contain a ${NAME} placeholder
  4. Description (optional): a note to help you recognise the secret later
  5. Click Add Secret

Rules

  • The value is encrypted on this device and is never shown again. The list shows a fixed •••••••• mask that says nothing about the value's length or content
  • To edit a secret, click Edit on its row. Leave Value blank to keep the stored value, or enter a new value to replace it, then click Save Changes
  • Keys must be unique
  • Names that CrewDeck provisions itself are reserved and rejected: GH_TOKEN, SONAR_API_KEY, CODACY_ACCOUNT_TOKEN, CREWDECK_BASE_BRANCH, CREWDECK_STOP_HOOK_DIR, CREWDECK_NOTIFICATION_HOOK_DIR and CREWDECK_GIT_GUARD_DIR
  • Names that change how a program is found or loaded are rejected: PATH, NODE_OPTIONS, HOME, SHELL, LD_PRELOAD, LD_LIBRARY_PATH and any name starting with DYLD_

Attaching a Secret to an MCP Server (New Relic example)​

  1. In Settings › AI & Tools › MCP Servers, add the server with Server Type http and the MCP endpoint URL from New Relic's documentation, then save it. Secrets can only be attached to a saved server, so click Edit on the server to reopen it
  2. In the server's Secrets area, click Attach Secret
  3. Choose your secret from Select a secret
  4. Enter the target name:
    • For an http server this is the Header name your provider documents. The field suggests Api-Key; use whatever header name New Relic's documentation gives
    • For a stdio server this is the Env var name the server reads, for example NEW_RELIC_API_KEY
  5. Click Save Secrets

Notes

  • A server can carry at most 32 attached secrets
  • The server must be enabled for the project the task runs in. Secrets attached to a server that is not enabled for the project are not passed to that run
  • If your provider needs a prefix, such as Authorization: Bearer <token>, type the header yourself in the server's Headers field as Authorization: Bearer ${NEW_RELIC_API_KEY}. CrewDeck keeps a reference you wrote rather than overwriting it
  • If the target name already holds a literal value, the attachment replaces that value with the reference
  • Host and Content-Length cannot be used as header names
  • Changing the Server Type between stdio and http invalidates existing attachments, because an env var only applies to stdio and a header only applies to http. A mismatched attachment is flagged and skipped at launch. Save the type change, reopen the server, correct the attachment's target name and click Save Secrets

The resulting entry in the worktree's .mcp.json holds only the reference, never the value:

{
  "mcpServers": {
    "new-relic": {
      "type": "http",
      "url": "https://<your-new-relic-mcp-endpoint>",
      "headers": { "Api-Key": "${NEW_RELIC_API_KEY}" }
    }
  }
}

How ${VAR} References Are Resolved​

  1. When a task runs, CrewDeck writes each server entry into the worktree's .mcp.json (and .codex/config.toml for Codex) with ${KEY} references only
  2. For the servers in that run, CrewDeck decrypts each attached value and places it in the agent run's environment
  3. The tool that launches the MCP server replaces each ${KEY} with the matching value from that environment
  • Only CrewDeck's own run environment is used to resolve a reference. Other variables from your shell are never consulted, so an unrelated environment variable cannot be pulled into a server's config
  • A reference that does not match an attached secret is left exactly as written, and the server reports a missing variable or fails to authenticate. A typo in a target name therefore shows up as an authentication failure, not as an error in Settings
  • If the operating system's credential store is unavailable or a value cannot be decrypted, that attachment is skipped with a warning and the run continues without it
  • Values are read again on every run. Nothing is cached between runs beyond the credential store's short-lived cache

Why Values Never Appear in Committed Config​

  • .mcp.json and .codex/config.toml only ever contain ${KEY} references, so committing or sharing them exposes no credential
  • The resolved value lives only in the agent run's environment and in the worktree's local .claude/settings.local.json. CrewDeck adds that file to the worktree's .gitignore, and when CrewDeck commits a run's work it also unstages it, together with .mcp.json and .codex/config.toml, so it does not end up in a commit or pull request. This is the same handling GH_TOKEN already gets
  • The value never comes back to the UI. Settings only ever receives the fixed mask
  • CrewDeck's own log and warning messages name the key or server, never the value
  • Terminal output masks a secret's literal value when it is between 8 and 512 characters long. Shorter or longer values are still passed to the server but are not masked in terminal output

Deleting or Rotating a Secret​

  • To delete a secret, click Delete on its row, then Confirm. The confirmation lists the servers that will lose the credential on their next run. Deleting removes the secret from every server it was attached to
  • Sessions that are already running keep the old value until they are restarted. If a key has leaked, also rotate it at the provider
  • Replacing a value, or attaching a secret to a server, takes effect on the next run

GitHub Token (GH_TOKEN) Setup Is Unchanged​

Connecting GitHub (Device Flow or Personal Access Token in Settings › Integrations) still provisions GH_TOKEN for the GitHub MCP server exactly as before. Custom secrets cannot use GH_TOKEN or any other CrewDeck-provisioned name, cannot override it, and do not change the GitHub server's generated config. Existing GitHub setups need no action.

Troubleshooting​

"Please connect GitHub in Settings first"​

Cause: GitHub is not authenticated.

Solution:

  1. Go to Settings
  2. Use Device Flow (recommended): click Sign in with GitHub, then visit github.com/login/device and enter the displayed code
  3. Alternatively, enter your GitHub Personal Access Token and click Connect GitHub
  4. Ensure the token has the repo scope (PAT method only)

GitHub Device Flow code not accepted​

Cause: The one-time code may have expired (codes are valid for approximately 15 minutes) or was entered incorrectly.

Solution:

  1. Return to Settings in CrewDeck and click Sign in with GitHub again to generate a new code
  2. Visit github.com/login/device promptly and enter the new code
  3. If the problem persists, fall back to Personal Access Token authentication

MCP server fails to authenticate after attaching a secret​

Cause: Any of the following:

  • The attachment was never saved (Save Secrets was not clicked), or it was removed
  • The secret was deleted, or its key was renamed while the server's Headers or Config still contain a ${KEY} reference you typed with the old name, so that reference is left unresolved
  • The server is not enabled for the project the task runs in
  • The Server Type was changed between stdio and http, and the attachment was not re-saved for the new type
  • The session started before the secret was attached or its value was replaced
  • The provider expects a different header or variable name, or a Bearer prefix
  • The operating system's credential store was unavailable, so the attachment was skipped with a warning

Solution:

  1. Open Settings › AI & Tools › MCP Servers, click Edit on the server and check that the secret is listed under Secrets. If not, attach it and click Save Secrets
  2. Check that the secret still exists under Secrets with the expected key
  3. Check that the server is enabled for the project
  4. If you changed the Server Type, save it, reopen the server, correct the flagged attachment and click Save Secrets
  5. Compare the target name with your provider's documentation. For a Bearer scheme, type Authorization: Bearer ${YOUR_KEY} in the server's Headers field
  6. Restart the session, or start a new run, so the current values are picked up

See Custom Secrets for MCP Servers for details.

What's New in v0.19.0​

Version 0.19.0 introduces JIRA integration, remote device pairing, session resume, and several improvements to the task execution pipeline.

JIRA Integration​

Connect your Atlassian JIRA Cloud instance to import issues as CrewDeck tasks and sync status changes back to JIRA. See Importing JIRA Issues as Tasks for setup instructions.

Remote Device Pairing​

Pair a remote device (phone, tablet, or secondary computer) with your CrewDeck instance using QR code scanning. Once paired, the remote device can monitor task progress and receive notifications. Pairing uses TLS-encrypted JWT authentication.

How to Pair

  1. Go to Settings > Remote Devices
  2. Click Generate Pairing Code
  3. Scan the QR code with the CrewDeck companion app on your device
  4. The device appears in the paired devices list

Session Resume​

Resume specific previous Claude CLI sessions by ID from the terminal panel. See Session Resume for details.

Task Completion Sentinel​

Agents can now emit a <TASK_COMPLETED/> sentinel token to signal task completion explicitly, improving detection reliability beyond process exit alone.

Sequential Relay Mode​

In sequential execution mode, agents can pass structured handoff files to the next agent in the chain, enabling explicit context transfer. Each handoff includes a summary, file list, and suggested next steps.

MCP Server Auto-Install​

Before agent execution, CrewDeck automatically runs npm install in any mcp-servers/ subdirectories in the worktree, ensuring MCP tool dependencies are available.

Sonar API Key Injection​

Configure a SonarCloud/SonarQube API key in Settings that is securely injected into agent sessions. See Sonar API Key in the Settings documentation.

Additional Improvements​

  • Credential notification auto-dismiss: Duplicate credential access notifications are suppressed with a 5-second auto-dismiss timer
  • excludeRules frontmatter: Agent YAML files now support excludeRules frontmatter for excluding specific rules during execution

Autonomy (Premium)​

Autonomy is a premium feature that automatically advances tasks through Kanban columns after successful execution. When enabled, completing a task in one stage (e.g., In Progress) automatically commits and pushes the working branch, moves the task to the next column (e.g., In Review), and begins execution of the next stage -- all without requiring the user to click "Run." In v0.25.0, autonomy was extended to automatically start the next todo task in the project after the current task reaches the Done stage, enabling fully autonomous task chaining across an entire project backlog.

How to Enable

  1. Go to Settings > AI & Tools
  2. Enable Turbo Mode (required prerequisite)
  3. Toggle Autonomy on

Multi-Agent DAG Execution (v0.37.0)​

Create complex multi-agent workflows with dependency relationships using Directed Acyclic Graph (DAG) execution mode.

When to Use DAG Mode​

  • Complex Dependencies: When one agent's output feeds directly into another agent's input
  • Conditional Branching: When you want certain agents to run only after others complete
  • Optimal Parallelization: The system automatically parallelizes agents with no dependencies on each other
  • Large Teams: Provides clearer visibility into multi-agent execution order for teams with 5+ agents

Creating a DAG Workflow​

  1. Create or edit a task with multiple agents
  2. In the execution mode selector, choose "DAG (Dependency graph)"
  3. The visual graph builder appears with all agents as nodes
  4. Drag arrows between agents to define dependencies (Agent A → Agent B means A must complete before B starts)
  5. Save the task with your graph configuration

Graph Editor Features​

  • Add Dependencies: Click and drag from one agent to another to create a dependency arrow
  • Remove Dependencies: Click on an arrow to delete it
  • Validate Graph: The system automatically detects and prevents circular dependencies
  • Reset Graph: Clear all dependencies and start fresh
  • Visual Feedback: Completed agents appear highlighted; agents ready to run are shown in blue

Execution Behavior​

  • Agents with no dependencies start immediately
  • Agents wait for all their dependencies to complete before starting
  • Multiple agents run in parallel when their dependencies allow
  • If any agent fails, dependent agents are blocked and marked as "waiting"
